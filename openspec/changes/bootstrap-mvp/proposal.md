# Proposal

## Why

情侣之间"今天谁带饭、带什么"每天都要口头协商，对方的忌口和口味靠记忆反复交代；饭带到了、吃到嘴里的那一刻，也没有任何留存。

外卖平台解决不了"记得你爱吃什么"，记账 App 解决不了"这顿饭的温度"。我们要的是一个**只用于工作日的私密带饭记录工具**：一方点菜、另一方带饭，把协商、偏好、交付和吃到的瞬间都沉淀下来。

## What Changes

系统从零建立，本次变更覆盖 MVP 全量能力：

- 建立微信小程序前端 + 自建 Spring Boot 后端（固定 2 人关系，不做多人）
- **情侣绑定**：微信登录、6 位邀请码配对、专属称呼、在一起纪念日、解绑（逻辑删除，记录保留）
- **点餐约定**：点餐方发起 / 带饭方主动带、认领、改派、取消，以及 `待认领 → 备餐中 → 已交付 → 已完成` 全状态机
- **超时自动流转**：11:00 未认领提醒、已交付超 24h 自动完成、次日 02:30 未交付转已过期、工作日 18:00 后不可约当天
- **菜单库与忌口**：菜品 CRUD、常点 / 忌口四级、口味画像、点餐时智能推荐与忌口提醒
- **爱心值**：约定完成给带饭方 +1，正向累计，不抵扣、不欠债、不参与任何结算
- **站内消息**：约定状态变化写入通知，Tab 红点，进列表即全部已读
- **吃饭打卡与饭桌相册**：接收方拍照 1–3 张 + 三档评价 + 点评，带饭方可回应，自动串成时间线相册
- **采购清单**：由约定菜品一键生成要买的东西，逐项勾选
- **共同周历**：一周谁带可视化
- **历史与报告**：历史列表按状态筛选，月度轻报告与年度带饭年报

**明确不做（范围边界，实现时不得自行放宽）**：

- 不做代投喂 / 代买 / 外卖 / 第三方代送——只限情侣亲手带饭
- 不碰真实支付，不存在任何金额、结算、欠债语义
- 不做多人关系、不做群组、不做公开排行榜
- 时段仅午饭，晚 / 加餐放二期

## Capabilities

### New Capabilities

- `couple-binding`: 微信登录与情侣关系生命周期——邀请码配对、专属称呼与纪念日、关系主页、解绑（逻辑删除、记录保留）
- `meal-plan`: 点餐约定的发起、认领、履约状态机、改派取消，以及全部超时自动流转规则
- `menu-prefs`: 菜单库与偏好记忆——菜品增删改查、常点与忌口四级、口味画像、点餐时的智能推荐与忌口提醒
- `love-value`: 爱心值——约定完成时给带饭方 +1、按约定幂等、累计与双方贡献展示
- `notifications`: 站内消息——状态变化的通知写入、未读红点、进列表即全量已读、按约定+类型去重
- `meal-checkin`: 吃饭打卡与饭桌相册——接收方拍照评价、带饭方回应、图片内容审核状态、按月时间线相册
- `plan-history`: 历史与报告——约定历史列表与状态筛选、月度轻报告、年度带饭年报
- `shopping-list`: 采购清单——由约定菜品生成要买项、逐项勾选已买
- `weekly-schedule`: 共同周历——一周带饭分工可视化

### Modified Capabilities

无。本变更为系统初始建立，`openspec/specs/` 目前为空。

## Impact

**代码**

- 全新工程，无既有代码需要迁移。前端 **uni-app（Vue3 + Vite + TS）**，编译目标仅微信小程序；后端 Spring Boot 3.4 + MyBatis-Plus + MySQL 8 单体，不引入 MQ / xxl-job。
- 数据模型 **12 张表**：`user` / `couple` / `couple_invite` / `meal_plan` / `meal_plan_item` / `menu_item` / `love_value` / `shopping_list` / `cancel_log` / `notification` / `meal_checkin` / `meal_checkin_image`。DDL 见 `db/schema.sql`。

**基础设施**

- 新建 MySQL 库 `couple_meal`（utf8mb4），与既有实例隔离。
- 需要**已备案的 HTTPS 域名**：小程序端请求（`uni.request`）强制 HTTPS，本机 localhost 与 IP 均不可用。
- 打卡照片存本机磁盘 `/data/upload/yyyyMM/` + Nginx 静态映射，图片域名同样须 HTTPS 且已备案。

**外部依赖**

- 微信小程序平台：`code2session` 登录、`security.mediaCheckAsync` 图片内容检测、`security.msgSecCheck` 文本检测。**UGC 图片未接检测会直接导致审核驳回**。
- 服务类目须选「工具 / 生活服务」，选「餐饮-外卖」会被要求《食品经营许可证》。

**文档输入**

- `docs/产品需求文档.md`、`docs/开发前准备与详细设计.md`、`docs/ui-prototype-cream.html` 是本次实现的规格来源；本变更的 specs 是它们的可验收摘要，冲突时以 specs 为准并回写 PRD。
