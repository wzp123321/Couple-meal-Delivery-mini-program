# Design

## Context

动机见 `proposal.md` 的 Why 一节。这里只记录影响实现方式的现状与约束：

- **全新工程**：仓库内目前只有文档（`docs/` 下的 PRD、开发前准备、HTML 原型）与协作文件，**没有一行业务代码**，因此不存在兼容或迁移包袱，一切按新建处理。
- **部署形态是单人单机**：团队只有一名开发者，服务跑在一台机器上，MySQL 复用本机已有实例（另开库）。这决定了所有技术选型都该偏向"少组件、可手工干预"。
- **硬约束**：不引入 MQ、xxl-job 等中间件；定时任务只能用 `@Scheduled`；单体分层，不拆服务。
- **平台约束**：小程序端请求（`uni.request`）强制 HTTPS 且域名必须备案，本机 localhost / IP 无法联调，开发期需内网穿透。有 UGC 图片就必须接微信内容安全检测，否则审核驳回。

## Goals / Non-Goals

**Goals（设计层面）**

- 状态流转与幂等**收敛到单点**，不留在各 Controller 里靠 if 判断——这是本项目最容易出错的地方（越级流转、重复加分）。
- 图片链路一次做对：压缩、格式白名单、剥离 EXIF、异步审核状态机。
- 定时流转在漏跑时可人工补，不依赖中间件的调度可靠性。
- 所有数据访问天然带关系隔离，不给越权留缺口。

**Non-Goals（设计层面，不是需求范围）**

- 不做多租户、不做水平扩展、不做读写分离——两人使用量级不构成设计压力。
- 不做对象存储与 CDN（二期），本期用本机磁盘。
- 不做 WebSocket 实时同步，靠"进页面拉取 + 下拉刷新 + 站内通知"。
- 不做接口版本化与灰度发布机制。

## Decisions

### 1. 单体分层 + 状态机单一入口

`controller / service / mapper / entity / dto / common` 六层，所有约定状态变更 MUST 经过 `PlanStateMachine`（Service 层），Controller 只做参数与鉴权，不得直接调用 Mapper 改 `status`。

**Why**：状态机有 7 个状态、多条边、还有超时自动流转，散落实现必然出现某条路径绕过校验。
**Alternatives**：① 每个业务方法内部自行判断状态 → 拒绝，校验点会随接口增加而发散；② 用状态机框架（Spring StateMachine）→ 对一个 7 状态的小模型过重，手写白名单更直观可测。

### 2. 幂等依赖数据库唯一索引，不依赖"先查后插"

三处必须幂等，全部用唯一索引兜底，捕获重复键异常后按"已处理"返回：

| 场景 | 约束 |
|---|---|
| 爱心值 +1 | `UNIQUE(plan_id, user_id)` |
| 打卡一次 | `UNIQUE(plan_id)` |
| 取消一次 | `UNIQUE(plan_id)` |

**Why**：两人可能同时点同一个按钮（尤其"已领取"），应用层"先查再插"在并发下有竞态。
**Alternatives**：Redis 分布式锁 → 单机单库场景属过度设计，且引入额外组件违反约束。

### 3. 定时任务用 `@Scheduled` + 条件 UPDATE

四个时点各一个方法，SQL 一律带状态条件（`UPDATE ... WHERE status = ? AND ...`），使重复执行天然幂等；每次执行记录起止与影响行数，并提供手动补跑入口。

**Why**：单机调度可能因重启漏跑，条件 UPDATE 保证补跑安全。
**Alternatives**：xxl-job → 违反"不引中间件"约束；数据库事件调度器 → 逻辑藏进 DB，难调试。

### 4. 图片：前端预压 + 服务端重新编码后落本机磁盘

- 前端用 `chooseMedia` 取图，压缩到长边 1080 后上传；
- 服务端**重新编码**（而非直接落盘），格式白名单 jpg/png/webp，重新编码天然剥离 EXIF；
- 存储路径 `/data/upload/yyyyMM/{uuid}.jpg`，文件名不用原始名；Nginx 静态映射，禁目录穿越。

**Why**：重新编码是最省事且最可靠的 EXIF 清除手段；按月分目录便于统计与清理。
**Alternatives**：① 直接存原始文件再单独清 EXIF 库 → 多一步且易漏；② 存 MySQL BLOB → 备份体积暴涨、静态服务不可用；③ 对象存储 → 二期，本期无必要。

### 5. 内容安全采用"先入库、异步改判"

打卡提交即入库并置 `audit_status=0`（审核中），异步调 `mediaCheckAsync`，回调更新为 1 通过 / 2 屏蔽。可见性规则：**打卡人始终可见自己的全部记录，另一方只见 `audit_status=1`**。

**Why**：同步等待检测会让用户提交后干等；而对本人隐藏会造成"我明明发了却看不到"的困惑。
**Alternatives**：同步阻塞等结果 → 体验差且检测可能数秒；先不入库等回调再入库 → 回调关联困难、打卡可能丢失。

### 6. 鉴权与隔离：自签 token + 上下文注入，`coupleId` 永不由前端传入

登录换 token，拦截器解析后把 `userId` 与 `coupleId` 放入请求上下文；Service 一律从上下文取 `coupleId`，接口入参不接受该字段。

**Why**：一旦 `coupleId` 可由前端传，改个参数就能读别人的数据（IDOR）。
**Alternatives**：每次查询由前端传 `coupleId` 并校验归属 → 校验点分散、易漏。

### 7. 前端用 uni-app（Vue3 + Vite + TS），编译目标仅微信小程序

**Why**：组件密度是这个项目的真实特征——7 个跨页组件 + 8 个弹层共用 `bottom-sheet` 容器，原生只能在 WXML 里靠 slot 传结构、靠 `triggerEvent` 逐层抛事件，而 Vue 的 `slot` / `emit` / `props` 是现成的；打卡上传是有状态 UI（逐张上传、单张重试、压缩进度），Vue 响应式比手动 `setData` 少一半代码。团队已熟 Vue3 + TS。
**Alternatives**：原生小程序 → 包体更小、微信新 API 零延迟，但 13 个页面要写 52 个文件，弹层与表单逻辑明显更啰嗦。**已评估并放弃**（2026-10-27 决策由原生改为 uni-app，触发因素是组件密度重估，多端能力只是顺带收益）。
**代价**：多一层编译；`chooseAvatar` / `type="nickname"` 两项微信独有能力需条件编译，M0 必须实测。

### 8. 状态枚举固定为 7 值

`0待认领 1待接收 2备餐中 3已交付 4已完成 5已取消 6已过期`，三个终态（4/5/6）不可再流转。

**Why**：已写入协作红线，前端角标、统计口径、定时任务都依赖这套值，中途变动成本高。
**Alternatives**：用字符串枚举 → 可读性好但索引与迁移更麻烦，且已有文档与红线按数字定义。

## Risks / Trade-offs

- **单机定时任务漏跑** → 条件 UPDATE 保证补跑安全；每次执行落日志与影响行数；提供手动补跑入口。
- **本机磁盘容量与丢失** → 单张 ≤1MB、按月分目录、总量 5GB 告警；`upload/` 目录与 MySQL 一起纳入每日备份（恋爱记录与照片都不可再生）。
- **24 小时自动完成可能违背当事人意愿** → 记录 `auto_confirmed` 来源标记，报告与年报里可区分"系统代确认"，避免被误当成对方主动领取。
- **内容安全异步存在时间窗** → 窗口内对方看不到照片属预期行为，文案明确写"审核通过后才会展示给 TA"，减少误解。
- **忌口只提醒不硬拦** → 明知过敏仍可能提交，这是产品已拍板的取向（体验优先、由人决定）；设计上不再加校验，只保证提醒足够醒目不遗漏。
- **uni-app 对微信新 API 支持滞后** → `chooseAvatar` / `type="nickname"` 在 M0 实测；不通过则用条件编译写原生标签绕过，不等做到设置页才发现。

## Migration Plan

全新系统，无存量数据迁移。上线顺序：

1. 建库 `couple_meal`（`utf8mb4` / `utf8mb4_0900_ai_ci`），执行建表脚本。
2. 后端部署到公网可达机器，配置 HTTPS 域名与 `/upload/` 静态映射，确认小程序后台的 request 与 downloadFile 合法域名已登记。
3. 小程序提审前自查：隐私协议弹窗、服务类目（工具 / 生活服务）、内容安全检测已接入、注销入口已具备。
4. 先用两个测试号（A/B）跑完约定全链路与打卡链路，再提交审核。

**回滚**：数据层按日备份，出错时可恢复到前一日快照；小程序版本在后台可回退到上一版本；后端为单体，回退即替换包。
