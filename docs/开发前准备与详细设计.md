## 1. 开发前准备清单（Checklist）

### 1.1 账号与平台
- [ ] **微信小程序账号**：注册并完成主体认证（个人/企业主体均可，个人号部分能力受限，订阅消息需企业号更易过审）。
- [ ] **AppID / AppSecret**：AppSecret 仅存后端配置，**严禁**进前端代码或代码库。
- [ ] **服务类目**：优先选「工具」或「生活服务-约会/情感」，**不要**选「餐饮-外卖/点餐」——后者会要求《食品经营许可证》，我们本质是私人记录工具，选错类目会卡审核。
- [ ] **微信开放平台**（可选）：若未来需 UnionID 打通多端，再绑定。

### 1.2 基础设施
- [ ] **公网域名 + HTTPS**：小程序 `wx.request` 强制 HTTPS，且必须是**已备案域名**，不能用 localhost / IP。开发期可用内网穿透（如 cpolar）临时联调，上线必须公网。
- [ ] **SSL 证书**：域名配 TLS（Let's Encrypt 免费即可）。
- [ ] **后端服务**：已有 Spring Boot 环境，需部署到公网可达的服务器/容器（云服务器 ECS 或轻量应用服务器）。
- [ ] **MySQL 8**：复用现有 MySQL 8 实例，新建独立库 `couple_meal`（注意与现有 18899 实例的库隔离）。
- [ ] **对象存储（二期）**：菜品图片用 OSS/COS，不存数据库。
- [ ] **微信后台配置**：「开发管理-服务器域名」填入 request 合法域名（https://你的域名）。

### 1.3 工程脚手架
- [ ] Spring Boot 3.4 + MyBatis-Plus 初始化，建库建表（见 PRD §7 DDL）。
- [ ] **统一响应体** `{code, msg, data}` + 全局异常处理器。
- [ ] **鉴权**：无状态 Token（JWT 或自定义），拦截器校验并注入当前用户。
- [ ] **基础 CRUD / 代码生成**：user / couple / meal_plan / menu_item / love_value / shopping_list。
- [ ] **日志与监控**：接口访问日志、异常告警（起码有错误日志落盘）。

### 1.4 合规与设计
- [ ] **隐私政策**：小程序必填，需说明收集 openid / 昵称 / 头像的用途。
- [ ] **授权流程**：`wx.login` 拿 code；头像昵称用新版头像昵称填写能力（不再有 `getUserProfile` 直接弹授权）。
- [ ] **UI 原型/设计稿**：建议开发前先用 Figma/墨刀画 Tab1–Tab3 + 约定详情 + 菜单库，避免边写边改。

## 2. 技术架构与接口规范

### 2.1 架构
```
微信小程序  ──HTTPS──>  Spring Boot(Controller→Service→Mapper)  ──>  MySQL 8
                          ↑ 拦截器校验 Token + 注入用户 + couple 隔离
```

### 2.2 鉴权流程
1. 小程序 `wx.login()` → 拿 `code`。
2. `POST /api/auth/login {code}` → 后端 `code2session` 换 `openid` → 建/查 `user` → 生成 `token` 返回。
3. 后续请求 Header `Authorization: Bearer <token>`；拦截器解析 → 注入 `currentUserId`。
4. **couple 隔离**：所有涉及数据的接口必须带 `couple_id` 并校验"当前用户属于该 couple"，防越权访问他人数据。

### 2.3 统一返回与状态码
```json
{ "code": 0, "msg": "ok", "data": {} }
```
- `code=0` 成功；`code>0` 业务失败；`code<0` 系统异常。
- 常见业务码：`1001` 未登录 / `1002` 无情侣关系 / `1003` 邀请码无效或过期 / `1004` 状态不允许该操作 / `1005` 不能认领自己的点餐。

## 4. 各模块异常与边界（细节周全）

### 4.1 关系 / 配对
- 邀请码 24h 过期；过期需重新生成。
- **并发加入**：两人同时用同一码加入 → 用 DB 唯一约束 / 事务，第二个报错"已被绑定"。
- 一方已绑定 → 禁止重复创建/加入，提示先解绑。
- **解绑后重绑**：逻辑删除旧 `couple`（`status=0`），新建关系；历史记录归属旧 `couple_id`，新关系看不到（符合 Q1"记录保留"= 旧关系数据留底，但不在新关系展示）。
- token 失效 → 前端静默用 `code` 重新登录。

### 4.2 点餐约定
- **同一天重复点餐**：允许（可能多餐），但前端可提示"今日已有约定"。
- **自己不能认领自己的点餐**（除非改派场景）。
- **状态越级防护**：服务端按 PRD §6.1 状态机校验，禁止 `待认领→已交付` 等跳变；非法流转返回 `1004`。
- **并发完成**：双方同时点"领取" → 爱心值按 `plan_id` 唯一索引幂等，只 +1。
- **取消后重发**：允许重新发起新约定；旧 `已取消` 记录留痕不参与统计。
- **跨天约定**：午饭约定若到次日仍未完成 → 状态保持，前端标"已过期"，不自动流转。
- **空菜品提交**：拦截，必须至少选/填一个菜。
- **备注长度**：`remark` 限 512 字，超长截断或报错。
- **主动带需确认接收**：`status=待接收`，A 确认后才 `备餐中`（防单方面决定）。
- **代投喂**：`is_proxy=1`，完成照常 +1 爱心，但"亲手做"徽章不计（Q4）。

### 4.3 菜单库
- 重名允许（归属不同：我/对方）。
- **删除被约定引用的菜品**：逻辑删除（加 `deleted` 标记），已发生的约定保留快照名称，不影响历史。
- **忌口冲突**：点餐选到对方 `avoid_level>=2` → 强提醒（Q2 不硬拦），仍可由人提交。
- 图片（二期）：存 OSS，库存 URL。

### 4.4 爱心值
- **幂等**：`love_value.plan_id` 唯一索引，重复触发报错忽略。
- **取消不扣**：仅 `已完成` 触发 +1；取消只针对非终态，不会误发。
- 并发：DB 唯一约束兜底。

### 4.5 消息
- 重复推送去重（按 `plan_id + 事件类型`）。
- 未读数：关系主页/红点展示，已读清理。
- 订阅消息授权失败 → 降级为系统内通知，不阻断主流程。

### 4.6 时间 / 时区
- 服务端统一 `Asia/Shanghai`，前端展示本地。
- 午饭约定默认 `plan_date = 今天`。

## 5. 安全与合规

- **越权防护**：所有接口校验"当前用户 ∈ 该 couple"，SQL 均带 `couple_id` 条件。
- **注入**：MyBatis-Plus 参数化，禁止字符串拼接。
- **敏感信息**：`openid` 不返回前端；token 不外泄。
- **隐私**：隐私政策 + 授权说明；仅收集必要信息。
- **限流**：登录/配对接口加简单限流，防刷邀请码。
- **HTTPS 全链路**：小程序强制，后端禁止明文。

## 6. 测试策略

- **单元**：Service 层——状态机流转、爱心值幂等、忌口提醒判定。
- **接口**：Postman / 自动化脚本覆盖 API 清单。
- **双人同步**：起两个测试号（A/B）联调配对、点餐、认领、完成全链路。
- **真机调试**：微信开发者工具 + 真机预览，验证登录、推送、图片（二期）。
- **边界用例**：过期邀请码、并发领取、自己认领自己、取消后重发、解绑后重绑。

## 7. 上线与审核

- **ICP 备案**：域名必须备案（国内服务器）。
- **提审材料**：功能截图、类目证明（我们选工具类，通常无需特殊资质）、隐私政策链接。
- **审核红线**：不得出现"支付/交易/外卖配送"等误导表述，文案走"投喂/约定"路线（与突出点 E 一致）。
- **灰度**：先小范围（自己双号）跑一周，再全量。
