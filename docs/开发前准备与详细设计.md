## 1. 开发前准备清单（Checklist）

### 1.1 账号与平台
- [ ] **微信小程序账号**：注册并完成主体认证（个人/企业主体均可，个人号部分能力受限，订阅消息需企业号更易过审）。
- [ ] **AppID / AppSecret**：AppSecret 仅存后端配置，**严禁**进前端代码或代码库。
- [ ] **服务类目**：优先选「工具」或「生活服务-约会/情感」，**不要**选「餐饮-外卖/点餐」——后者会要求《食品经营许可证》，我们本质是私人记录工具，选错类目会卡审核。
- [ ] **微信开放平台**（可选）：若未来需 UnionID 打通多端，再绑定。

### 1.2 基础设施
- [ ] **公网域名 + HTTPS**：小程序端请求（`uni.request`）强制 HTTPS，且必须是**已备案域名**，不能用 localhost / IP。开发期可用内网穿透（如 cpolar）临时联调，上线必须公网。
- [ ] **SSL 证书**：域名配 TLS（Let's Encrypt 免费即可）。
- [ ] **后端服务**：已有 Spring Boot 环境，需部署到公网可达的服务器/容器（云服务器 ECS 或轻量应用服务器）。
- [ ] **MySQL 8**：复用现有 MySQL 8 实例，新建独立库 `couple_meal`（注意与现有 18899 实例的库隔离）。
- [ ] **打卡照片存储（MVP 必做）**：本机磁盘 `/data/upload/yyyyMM/`，Nginx 静态映射为 `https://你的域名/upload/...`。**图片域名同样要 HTTPS + 备案**，否则小程序 `<image>` 加载不出来。
- [ ] **磁盘容量**：单张压到 ≤1MB、长边 1080，两人日常用量一年约 1–2GB；设 5GB 告警。
- [ ] **对象存储（二期）**：菜单库菜品图 + 相册迁移用 OSS/COS，不存数据库。
- [ ] **微信后台配置**：「开发管理-服务器域名」填入 request 合法域名（https://你的域名）。

### 1.3 工程脚手架
- [ ] Spring Boot 3.4 + MyBatis-Plus 初始化，建库建表（**直接执行 `db/schema.sql`，12 张表**；PRD §7 与之一一对应）。
- [ ] **统一响应体** `{code, msg, data}` + 全局异常处理器。
- [ ] **鉴权**：无状态 Token（JWT 或自定义），拦截器校验并注入当前用户。
- [ ] **基础 CRUD / 代码生成**：user / couple / couple_invite / meal_plan / meal_plan_item / menu_item / love_value / shopping_list / cancel_log / notification / meal_checkin / **meal_checkin_image**（12 张，与 `db/schema.sql` 一致）。
- [ ] **日志与监控**：接口访问日志、异常告警（起码有错误日志落盘）。

### 1.4 合规与设计
- [ ] **隐私政策**：小程序必填，需说明收集 openid / 昵称 / 头像的用途。
- [ ] **授权流程**：`uni.login` 拿 code；头像昵称用新版头像昵称填写能力（不再有 `getUserProfile` 直接弹授权），`chooseAvatar` / `type="nickname"` 属微信专有能力，需条件编译。
- [ ] **UI 原型/设计稿**：建议开发前先用 Figma/墨刀画 Tab1–Tab3 + 约定详情 + 菜单库，避免边写边改。

## 2. 技术架构与接口规范

### 2.1 架构
```
微信小程序  ──HTTPS──>  Spring Boot(Controller→Service→Mapper)  ──>  MySQL 8
                          ↑ 拦截器校验 Token + 注入用户 + couple 隔离
```

### 2.2 鉴权流程
1. 小程序 `uni.login()` → 拿 `code`。
2. `POST /api/auth/login {code}` → 后端 `code2session` 换 `openid` → 建/查 `user` → 生成 `token` 返回。
3. 后续请求 Header `Authorization: Bearer <token>`；拦截器解析 → 注入 `currentUserId`。
4. **couple 隔离**：所有涉及数据的接口必须带 `couple_id` 并校验"当前用户属于该 couple"，防越权访问他人数据。

### 2.3 统一返回与状态码
```json
{ "code": 0, "msg": "ok", "data": {} }
```
- `code=0` 成功；`code>0` 业务失败；`code<0` 系统异常。
- 常见业务码：`1001` 未登录 / `1002` 无情侣关系 / `1003` 邀请码无效或过期 / `1004` 状态不允许该操作 / `1005` 不能认领自己的点餐。

## 4. 各模块异常与边界（细节周全）

### 4.1 关系 / 配对
- 邀请码 24h 过期；过期需重新生成。
- **并发加入**：两人同时用同一码加入 → 用 DB 唯一约束 / 事务，第二个报错"已被绑定"。
- 一方已绑定 → 禁止重复创建/加入，提示先解绑。
- **解绑后重绑**：逻辑删除旧 `couple`（`status=0`），新建关系；历史记录归属旧 `couple_id`，新关系看不到（符合 Q1"记录保留"= 旧关系数据留底，但不在新关系展示）。
- token 失效 → 前端静默用 `code` 重新登录。

### 4.2 点餐约定
- **同一天重复点餐**：允许（可能多餐），但前端可提示"今日已有约定"。
- **自己不能认领自己的点餐**（除非改派场景）。
- **状态越级防护**：服务端按 PRD §6.1 状态机校验，禁止 `待认领→已交付` 等跳变；非法流转返回 `1004`。
- **并发完成**：双方同时点"领取" → 爱心值按 `plan_id` 唯一索引幂等，只 +1。
- **取消后重发**：允许重新发起新约定；旧 `已取消` 记录留痕不参与统计。
- **跨天约定**：次日 02:30 仍未交付（待认领/待接收/备餐中）→ 定时任务置 `status=6 已过期` 并归档历史，不发爱心值；已交付的不参与过期，由超 24h 自动完成收尾（PRD §12.6）。
- **已交付超 24h 未领取**：自动转 `已完成` 并照发爱心值，防一方故意不点卡流程；定时任务实现，需记录 `auto_confirmed` 来源便于追溯。
- **空菜品提交**：拦截，必须至少选/填一个菜。
- **备注长度**：`remark` 限 512 字，超长截断或报错。
- **主动带需确认接收**：`status=待接收`，A 确认后才 `备餐中`（防单方面决定）。

### 4.3 菜单库
- 重名允许（归属不同：我/对方）。
- **删除被约定引用的菜品**：逻辑删除（`status` 置 `2`），已发生的约定保留菜名快照，不影响历史。
- **忌口冲突**：点餐选到对方 `avoid_level>=2` → 强提醒（Q2 不硬拦），仍可由人提交。
- 图片（二期）：存 OSS，库存 URL。

### 4.4 爱心值
- **幂等**：`love_value(plan_id, user_id)` 复合唯一索引，重复触发报错忽略。
- **取消不扣**：仅 `已完成` 触发 +1；取消只针对非终态，不会误发。
- 并发：DB 唯一约束兜底。

### 4.5 消息
- 重复推送去重（按 `plan_id + 事件类型`）。
- 未读数 = `notification(receiver_id=我, read_flag=0)`；**进消息列表即全量置已读**，Tab 角标同步清零（PRD §12.5）。
- 角标 `>99` 显示 `99+`，`=0` 隐藏。
- 已完成 / 已取消 / 已过期的通知保留在列表，只是不再计未读。
- 订阅消息授权失败 → 降级为系统内通知，不阻断主流程。

### 4.6 时间 / 时区
- 服务端统一 `Asia/Shanghai`，前端展示本地。
- 午饭约定默认 `plan_date = 今天`；**仅工作日（周一~周五）自动排/提醒，周末不自动发起**。

### 4.7 吃饭打卡（饭桌相册）
- **打卡窗口**：`status ∈ {已交付, 已完成}` 且 `plan_date` 为今天或昨天；窗口到次日 **02:00** 结束，逾期拒绝（防"月底批量补打卡"刷数据）。前端在未交付时就不显示按钮。
- **谁能打**：仅 `orderer_id == 当前用户`（接收方）；带饭方调用直接 `1004`。
- **一个约定一次**：`uk_meal_checkin_plan` 唯一索引兜底；重复提交返回"已经记过啦"，引导走改打卡而不是新建。
- **图片数量**：1–3 张，**服务端二次校验**（前端限制可绕过）。
- **图片安全**：提交后 `audit_status=0`，调 `mediaCheckAsync` 异步回调置 1 通过 / 2 屏蔽；`gallery` 与**对方视角只返回 `audit_status=1`**，本人可见自己的全部（否则用户不知道为什么"我发了却看不到"）。
- **路径安全**：`images` 只接受服务端生成的相对路径，拒绝外部 URL（防 SSRF / 盗链）。
- **文件处理**：单张 ≤1MB、仅 jpg/png/webp；服务端**重新编码压缩并剥离 EXIF**——用户随手拍的照片带 GPS，不剥离等于泄露住址。
- **改打卡**：当天可改评价 / 点评 / 换图；**不提供删除**（删了记忆就断），真删走设置里的数据删除入口。
- **回应**：仅 `carrier_id` 可回应，≤50 字，覆盖更新不新增记录。
- **不写爱心值**：打卡不触发 `love_value`，爱心值仍只由 `已完成` 触发，避免为刷分而打卡。
- **统计口径**：相册统计与"一起吃饭天数"只算 `meal_checkin`，不掺 `meal_plan`，避免过期/取消的约定污染。

## 5. 安全与合规

- **越权防护**：所有接口校验"当前用户 ∈ 该 couple"，SQL 均带 `couple_id` 条件。
- **注入**：MyBatis-Plus 参数化，禁止字符串拼接。
- **敏感信息**：`openid` 不返回前端；token 不外泄。
- **隐私**：隐私政策 + 授权说明；仅收集必要信息。
- **限流**：登录/配对接口加简单限流，防刷邀请码。
- **UGC 内容安全（打卡必做）**：文本走 `msgSecCheck` + 本地敏感词；图片走 `security.mediaCheckAsync` 异步检测，**未通过不展示**。这是小程序有用户上传图片的审核硬门槛，不做会驳回。
- **图片访问**：`/upload/` 目录禁止 `..` 路径穿越，只允许白名单后缀；文件名用 UUID，不用原始文件名。
- **EXIF 剥离**：照片重新编码时丢掉 GPS 等元数据，避免泄露家庭 / 公司位置。
- **HTTPS 全链路**：小程序强制，后端禁止明文。

## 7. 上线与审核

- **ICP 备案**：域名必须备案（国内服务器）。
- **提审材料**：功能截图、类目证明（我们选工具类，通常无需特殊资质）、隐私政策链接。
- **审核红线**：不得出现"支付/交易/外卖配送"等误导表述，文案走"投喂/约定"路线（与突出点 E 一致）。
- **UGC 能力申报**：有用户上传图片，提审时需说明已接内容安全检测（`mediaCheckAsync`），并具备违规内容屏蔽 / 删除能力，否则驳回。
- **图片域名合规**：`/upload/` 所在的图片域名同样要 HTTPS + 备案，且与 request 域名一致或在 `downloadFile` 合法域名里。
- **灰度**：先小范围（自己双号）跑一周，再全量。
