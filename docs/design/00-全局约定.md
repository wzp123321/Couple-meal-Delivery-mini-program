## 1. 设计决策（D1–D16）

| 编号 | 决策点 | 选择 | 理由 | 代价 |
|---|---|---|---|---|
| D1 | 主键策略 | **`BIGINT NOT NULL` + 雪花 ID，禁自增** | 对齐公司 SQL 规范；`id` 会返给小程序，JS `Number` 只有 53 位精度，标准 64bit 雪花直接返回会丢位 | 需自实现 53bit 雪花生成器（见 `后端-00-架构.md` §5）；ID 不可读，排查靠业务字段 |
| D2 | 约定菜品存储 | **新增 `meal_plan_item` 子表** | 口味画像要按菜品聚合统计（"最常点的菜"），逗号串无法 SQL 聚合；子表顺带解决"菜单改名污染历史"——存菜名快照 | 多一张表、详情页多一次查询（可批量查） |
| D3 | 邀请码存储 | **新增 `couple_invite` 表** | PRD §5.1 要求 6 位码 / 24h / 一次性 / 限频，初版 9 张表无处承载（PRD §7 已同步为 12 张） | 多一张表；`uk_couple_invite_code` 唯一索引在码过期后不释放（6 位数字 90 万空间，个人体量无影响） |
| D4 | 打卡图片审核粒度 | **拆 `meal_checkin_image` 子表** | `mediaCheckAsync` 异步回调只带 `trace_id`，必须能定位"2 张里坏的是哪 1 张"；单字段只能整条屏蔽，会误伤整条打卡且无法恢复 | 多一张表；相册查询多一次 IN 查询 |
| D5 | 软删除范围 | 仅 `menu_item` 软删；`meal_plan` 靠 `status` 区分终态，不做软删 | 菜单硬删会破坏口味画像的历史统计；约定本身有 5/6 终态，不需要再叠一层删除标记 | 无 |
| D6 | 解绑后复合 | **复活原 `couple` 记录**（`status` 置回 1），不新建 | `uk_couple_pair(user_a,user_b)` 唯一索引会拦住新建；复活同时保住了历史数据关联 | 需在 `join` 逻辑里先查历史记录再决定 insert / update |
| D7 | 爱心值幂等 | 唯一索引 `uk_love_value_plan_user(plan_id,user_id)` 兜底，应用层**不做**「先查再插」 | 并发下"先查再插"必然漏判；让数据库拒绝重复，代码 catch `DuplicateKeyException` 当成功处理 | 需要捕获特定异常，不能笼统 catch |
| D8 | 状态流转入口 | 集中到 `PlanStateMachine`，**Controller 一律不收 `status` 入参** | 状态由具体动作（claim/deliver/complete）推导，前端无法传入任意状态；越权与越级在单点拦截 | 新增动作要改状态机白名单 |
| D9 | 并发控制 | 状态类更新用**条件 UPDATE + affected rows 判断**，不用悲观锁 | `update ... where id=? and status=?` 天然串行，抢不到就是 0 行，直接返回"状态已变化"；比 `select for update` 少一次往返 | 需统一封装成 `updateStatus(id, from, to)` |
| D10 | 定时任务 | 单机 `@Scheduled` 四个 Job，不引入 xxl-job / MQ | PRD §12.6 已拍板单体；单实例部署无重复执行问题 | 未来多实例部署必须加分布式锁（届时再说） |
| D11 | 过期时点 | **次日 02:30 仍未交付**（仅 0/1/2 三种状态） | 与打卡窗口（至次日 02:00）、权限矩阵（已过期不可打卡）对齐；只对未交付的判过期，已交付交给 24h 自动完成 | 无 |
| D12 | 图片存储 | 本机磁盘 `/data/upload/yyyyMM/`，Nginx 静态映射，库内**只存相对路径** | 换存储（OSS）时只改前缀，不动数据 | 迁移需批量刷 URL |
| D13 | 雪花 ID 位宽 | **53bit**：时间位 + 序列位，**省略节点位** | 单实例部署不需要多节点标识；53bit 保证 `Number.MAX_SAFE_INTEGER` 内精确表示，小程序拿到 ID 不丢精度 | 将来多实例部署需挤入节点标识或改 64bit + 前端按字符串接收 |
| D14 | 公共字段 | **三列**：`id` + `create_time` + `update_time`（公司规范为四列） | 公司第四列 `row_update_time` 定义与 `update_time` 完全相同（都 `ON UPDATE CURRENT_TIMESTAMP`），本项目无多系统数据同步场景，加它是纯冗余 | 与公司建表脚本不完全一致；若并入公司体系需补该列 |
| D15 | 认领路径 | **一步到位**：`待认领 --claim--> 备餐中`；「待接收」只属于主动带（`source=1`） | 点餐场景双方在线下已说好，认领后再由点餐方确认一次纯属多余；主动带才需要接收方点头 | 状态机两条入口在「备餐中」汇合；`withdraw` 仅点餐场景可用，主动带回退等于 `cancel` |
| D16 | 头像存储与审核 | **上传到 `/data/upload/avatar/`，长边 256、≤100KB，同步 `imgSecCheck` 通过后才落盘** | `chooseAvatar` 返回的是**本地临时路径**（`http://tmp/...`），不是可持久 URL，必须上传；头像小图走同步审核比 `mediaCheckAsync` 简单——不过审直接拒绝，不用拆子表也不用回调 | 多一个上传接口；同步审核让保存头像慢 100–300ms；`user.avatar` 由 `NULL` 变为有值后，PRD「唯一图片场景」的口径改为两处 |

> **落库前先读 §2.1 建表约定**，命名违规会连带影响 Mapper 与 DO 的字段映射。

### 2.1 建表约定（对齐公司 SQL 规范）

| 项 | 规则 | 备注 |
|---|---|---|
| 主键 | `id BIGINT NOT NULL`，**雪花 ID、禁自增** | 见 D1 / D13；MyBatis-Plus 用 `@TableId(type = IdType.ASSIGN_ID)` |
| 公共字段 | `create_time` + `update_time` | 公司第四列 `row_update_time` 不加，见 D14 |
| 禁用字段 | `create_by` / `update_by` / `delete_flag` 一律不出现 | 软删统一用 `status` |
| 布尔命名 | 一律 `_flag` / `_status` 后缀 | **禁 `is_` 开头**：`favorite_flag` / `read_flag` / `checked_flag` |
| 时间列命名 | 一律 `_time` 后缀，不用 `_at` | `claimed_time` / `delivered_time` / `expire_time` |
| 索引命名 | `uk_{表名}_{字段}` / `idx_{表名}_{字段}` | 带表名，跨表同名不冲突 |
| 建表脚本 | `CREATE TABLE IF NOT EXISTS` | 可重复执行 |
| 外键 | 不使用 | 一致性由服务层保证，与公司脚本一致 |

> **`menu_item` 软删特例**：`status` 同时承担数据状态（`0` 异常 / `1` 正常 / `2` 已删除），**所有查询必须带 `status = 1`**；删除即 `UPDATE ... SET status = 2`。漏这个条件，删掉的菜会重新出现在菜单库。

## 3. 鉴权与数据隔离

1. **Token**：JWT，`Authorization: Bearer <token>`，30 天有效。
2. **拦截器**：解析 token → `UserContext.setUserId(uid)`；`coupleId` **不放进 token**，由拦截器实时查一次（带本地缓存，60 秒过期）。
3. **数据隔离铁律**：`coupleId` 只从 `UserContext` 取，**任何接口都不接受前端传入 `coupleId`**。所有 Mapper 查询必须带 `couple_id = #{ctx.coupleId}` 条件。
4. **越权兜底**：按业务 ID（如 `planId`）查出来的记录，必须再校验一次 `record.coupleId == ctx.coupleId`，不等则返回 `1002`（与"无关系"同一码，不泄露"这条数据存在但不属于你"）。
5. **免鉴权路径**：`/api/auth/login`、`/api/wx/media-check-callback`、`/upload/**`（静态图）。

> 这 5 条是**每个接口都要满足**的，不是某模块专属。模块文档不再重复，实现时逐条自检。

## 5. 配置项

```yaml
couple-meal:
  jwt:
    secret: ${JWT_SECRET}          # 必须从环境变量注入，禁止进代码库

  wx:
    appid: ${WX_APPID}
    secret: ${WX_SECRET}           # 仅后端持有
  upload:
    base-dir: /data/upload
    url-prefix: https://你的域名/upload
    max-raw-size: 10485760         # 原始图上限 10MB
    max-output-size: 512000        # 原图压缩后上限 500KB
    max-edge: 1080

    max-items: 10
    max-date-ahead-days: 7
  schedule:
    expire-cron: "0 30 2 * * *"    # 见 01-通用机制.md §4.2
    auto-complete-cron: "0 0 * * * *"
    invite-expire-cron: "0 0 * * * *"
    daily-remind-cron: "0 0 11 * * MON-FRI"
```

## 6. 已知取舍（全局，模块内的取舍写在各模块文档末尾）

| 取舍 | 说明 | 何时该改 |
|---|---|---|
| 爱心值不做冗余计数列 | 每次 `SUM(delta)`，两人一年几百条无压力 | 单 couple 流水破万时加计数字段 |
| 邀请码过期不释放 | 6 位数字空间 90 万，个人产品够用 | 若做开放注册需回收 |
| 图片存相对路径 | 换 OSS 只改前缀 | 迁移时批量刷 DB |
| 单机 `@Scheduled` | 简单，够用 | 多实例部署前必须加分布式锁 |
| 审核回调不验签 | 微信机制如此 | 用随机路径段 + trace_id 存在性校验兜底 |
| 不接微信订阅消息 | MVP 用站内红点 | 二期接 `subscribeMessage` |
