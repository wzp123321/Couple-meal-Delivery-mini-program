## 1. 数据表

### `menu_item`

| 字段 | 类型 | 说明 |
|---|---|---|
| `couple_id` | BIGINT | 关系隔离键 |
| `name` | VARCHAR(64) | 菜名 **≤20 字** |
| `category` | TINYINT | `1` 荤 / `2` 素 / `3` 汤 / `4` 主食 |
| `favorite_flag` | TINYINT | `0` 普通 / `1` 常点（**UI 文案统一叫「常点★」**，接口参数 `onlyFavorite`，三者指同一件事） |
| `avoid_level` | TINYINT | `0` 无 / `1` 少吃 / `2` 不吃 / `3` 过敏（**只提醒不硬拦**） |
| `creator_id` | BIGINT | 谁加的菜（区分「我的」「TA 的」） |
| `note` | VARCHAR(512) NULL | 菜谱笔记（**二期启用**，MVP 不写入） |
| `status` | TINYINT | `0` 异常 / `1` 正常 / `2` 已删除（**软删**，D5） |

**两条索引**：

| 索引 | 服务的查询 |
|---|---|
| `idx_menu_item_couple_status_category(couple_id, status, category)` | 菜单库按分类筛选 |
| `idx_menu_item_couple_status_name(couple_id, status, name)` | 同关系内重名校验 |

> **为什么软删**：口味画像要统计历史，硬删会丢数据。所有查询必须带 `status=1`。

## 3. 实现

### 3.1 新增 / 修改

1. `name` 去首尾空格，长度 ≤20 → 否则 `2004`。
2. 同关系内重名校验：`select ... where couple_id=? and status=1 and name=?`，命中 → `2002`。
   **修改时排除自己**（`and id != ?`）。
3. `category` / `avoidLevel` 必须在枚举范围内，非法值 → `2004`。

### 3.2 列表与「最近点过」排序

默认按 `create_time DESC`；`sort=recent` 时按**这道菜最近被点过的日期**倒序，从没点过的排最后。

```sql
SELECT mi.*, MAX(p.plan_date) AS last_ordered
FROM menu_item mi
LEFT JOIN meal_plan_item pi ON pi.menu_item_id = mi.id
LEFT JOIN meal_plan p ON p.id = pi.plan_id AND p.couple_id = mi.couple_id
                      AND p.status NOT IN (5, 6)   -- 条件写 ON，否则 LEFT JOIN 退化成 INNER
WHERE mi.couple_id = ? AND mi.status = 1
  AND (/* category / is_favorite / creator_id 条件 */)
GROUP BY mi.id
ORDER BY last_ordered IS NULL, last_ordered DESC, mi.create_time DESC;
```

- **只排除已取消 / 已过期**（`p.status NOT IN (5,6)`），进行中的约定也算"点过"，方便当天再点一次。
- 手输菜名（`menu_item_id IS NULL`）不参与——它本来就没关联菜品，只进历史。
- 排序必须在 SQL 里做，不能取回内存排：菜单可能上百条且要分页。

### 3.3 删除

`UPDATE menu_item SET status=2 WHERE id=? AND couple_id=?`。
**不动 `meal_plan_item`** —— 那里存的是菜名快照，删菜单不影响任何历史约定。

### 3.4 口味画像（`/api/menu/profile`）

按 `meal_plan_item.name` 聚合，**不是** join `menu_item`：

```sql
-- 最常点的菜（Top 5）
SELECT i.name, COUNT(*) AS cnt
FROM meal_plan_item i
JOIN meal_plan p ON p.id = i.plan_id
WHERE p.couple_id = ? AND p.status = 4          -- 只统计已完成
GROUP BY i.name
ORDER BY cnt DESC
LIMIT 5;
```

- 只统计 `status=4` 的约定（吃了的才算数，取消/过期的不计）。
- 这是 D2 新增 `meal_plan_item` 的**唯一理由**——逗号串无法做这个聚合。

### 3.5 智能推荐（`/api/menu/recommend`）

规则（按顺序）：

1. **排除** `avoid_level >= 2`（不吃 / 过敏）—— 推荐里绝不出现。
2. **优先** `favorite_flag=1`。
3. 其次是距离上次点单最久的菜（避免连续重复）。
4. 数量不足时用同分类其他菜补足。

> 推荐是"锦上添花"，不做复杂算法，**纯 SQL + 规则**即可。

### 3.6 忌口语义

`avoid_level` **只用于提醒，不做服务端拦截**（PRD Q2 拍板）：

- 发起约定时命中 → 返回 `warnings`，由前端弹强提醒（见 `../20-约定/后端.md §3.1`）。
- 列表接口按级别排序：`3 过敏` 置顶，`2 不吃` 次之（排序在 SQL 的 `ORDER BY` 里做，前端不再重排）。

## 5. 验收要点

对照 `openspec/changes/bootstrap-mvp/specs/menu-prefs/spec.md`：

- [ ] 同关系内重名返回 2002；不同关系（另一对情侣）同名不冲突
- [ ] 菜名超 20 字返回 2004
- [ ] 删除为软删，列表不显示但历史约定仍显示原菜名
- [ ] 口味画像只统计已完成（`status=4`）的约定
- [ ] 推荐结果**不含** `avoid_level >= 2` 的菜
- [ ] 忌口命中不阻断提交，仅返回 warnings

## 6. 易错点

| 坑 | 说明 |
|---|---|
| 查询漏 `status=1` | 软删的菜会重新出现在列表里 |
| 重名校验没排除自己 | 编辑时只要不改名就一定报 2002 |
| 口味画像 join `menu_item` | 菜单改名后统计会算错/漏算。**必须聚合 `meal_plan_item.name`** |
| 在服务端硬拦忌口 | PRD Q2 明确"只提醒不硬拦"，拦截会让用户无法点自己想吃的东西 |
