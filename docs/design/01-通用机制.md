## 1. 状态机

### 1.1 状态与转移图

两条入口在「备餐中」汇合，汇合后流程完全一致。

```
点餐   source=0 : 0 待认领 ──claim(B)─────┐
                     ▲                    │
                     └──── withdraw(B) ───┘   退回待认领（改派）

主动带 source=1 : 1 待接收 ──confirm(A)───┤
                     │                    │
                     └── reject(A) ──> 5 已取消
                                          ▼
                    2 备餐中 ──deliver(B)──> 3 已交付 ──complete(A)──> 4 已完成
                                                │
                                                └── autoComplete(系统, 超24h) ──> 4 已完成

旁路：0/1/2/3 ──cancel(双方)──> 5 已取消
      0/1/2   ──expire(系统)──> 6 已过期
```

- 点餐（`source=0`）创建落在 `0 待认领`，对方认领后**直接进备餐中**，无二次确认。
- 主动带（`source=1`）创建即落在 `1 待接收`，因为"谁带"由发起人自带，需要接收方点头。
- **待接收只属于主动带**：点餐场景不会出现 `status=1`。
- `withdraw` 是带饭方**退回待认领**（改派），不是取消，不写 `cancel_log`；仅点餐场景可用——主动带没有"待认领"可回，撤回等于 `cancel`。

### 1.2 转移白名单（`assertCan(action, plan, me)` 判定表）

| action | 前置 status | 操作人 | 后置 status |
|---|---|---|---|
| `claim` | 0（`source=0`） | ≠ orderer | **2** |
| `withdraw` | 2（`source=0`） | = carrier | 0 |
| `confirm` | 1（`source=1`） | = orderer | 2 |
| `reject` | 1（`source=1`） | = orderer | 5 |
| `deliver` | 2 | = carrier | 3 |
| `complete` | 3 | = orderer | 4 |
| `cancel` | 0/1/2/3 | 双方皆可 | 5 |
| `expire` | 0/1/2 | 系统 | 6 |
| `autoComplete` | 3 | 系统 | 4 |

**终态 4/5/6 一律只读**，任何 action 进来都返回 `1004`。

### 1.3 实现方式

`PlanStateMachine` 内部是一张 `Map<PlanAction, Transition(fromSet, role, to)>` 静态表，
`assertCan` 查表 + 校验 `role`，然后走统一的条件 UPDATE。**新增动作只需加一行表项**，不会散落 if-else。

```java
// 唯一的状态写入方式
int n = planMapper.updateStatus(id, from, to, version);
if (n == 0) throw new BizException(ErrorCode.STATUS_CONFLICT); // 1004
```

- 状态机**只做**白名单校验 + 条件更新，**不做**通知、爱心值等副作用（由 Service 编排，见各模块文档）。
- Controller **一律不接收 `status` 入参**（D8）。状态由具体动作推导。

## 2. 并发与幂等

| 场景 | 风险 | 解法 | 归属模块 |
|---|---|---|---|
| 两人同时点「认领」 | 重复认领 | 条件 UPDATE + `affected rows` | `20` |
| 两人同时点「取消」 | 双写 `cancel_log` | `uk_cancel_log_plan` 拒绝第二条 | `20` |
| 重复点「完成」 | 爱心值 +2 | 状态条件更新（第二次 0 行）+ `uk_love_value_plan_user` | `20` / `40` |
| 两人同时用同一邀请码 | 一人绑上两段关系 | `select for update` + 唯一关系校验 | `10` |
| 重复点「生成清单」 | 条目翻倍 | `uk_shopping_list_plan_item(plan_id, item_name)` | `80` |
| 审核回调重复推送 | 状态抖动 | 按 `trace_id` 定值 update，同值重复无副作用 | `60` |
| 通知重复触发 | 红点跳数 | `uk_notification_plan_type_receiver` | `50` |

**四条通用原则**

1. **能靠唯一索引的，不靠应用层判断**。并发下"先查再插"必然漏判。
2. **状态类更新一律条件 UPDATE + affected rows**，不引 `select for update`（D9）。
3. **捕获 `DuplicateKeyException` 视为成功**（幂等语义），不能笼统 catch `Exception`。
4. **副作用放状态更新成功之后**，避免"通知发了但状态没改"。

## 3. 事务边界

- **只在 Service 的写方法上开** `@Transactional`，读方法不加。
- 跨服务副作用（通知、爱心值）在状态更新成功之后调用，但仍处于同一事务内（保证状态与流水一致）；
  若希望通知不阻塞主事务，才改为事务提交后异步——MVP **不这么做**，简单优先。
- 单个事务内不调外部 HTTP（微信接口）。打卡提交时的 `mediaCheckAsync` 是例外，见 `60-打卡/后端.md §3.2` 的处理。

## 4. 定时任务

四个 Job 全部 `@Scheduled`，cron 从配置读（见 `00-全局约定.md §5`），单机无需分布式锁。

### 4.1 总表

| Job | cron | 动作 | 详解在 |
|---|---|---|---|
| `PlanExpireJob` | `0 30 2 * * *` | `status ∈ (0,1,2) and plan_date <= 昨天` → 6 | §4.2 |
| `AutoCompleteJob` | `0 0 * * * *` | `status=3 and delivered_time < now()-24h` → 4 + 爱心值 | `20-约定/后端.md §4` |
| `InviteExpireJob` | `0 0 * * * *` | `status=0 and expire_time < now` → 2 | `10-关系绑定/后端.md §4` |
| `DailyRemindJob` | `0 0 11 * * MON-FRI` | `status=0 and plan_date=今天` → 通知带饭方 | `50-通知/后端.md §4` |

### 4.2 过期时点（D11）

| 项 | 规则 |
|---|---|
| 执行时点 | 次日 **02:30** |
| 处理对象 | `status ∈ (0,1,2)` 且 `plan_date <= 昨天` |
| 不处理 | `status = 3`（已交付）——已交付走 24h 自动完成，不受过期影响 |
| 结果 | 转 `status = 6`，归档历史，不发爱心值 |

```sql
UPDATE meal_plan
SET status = 6, version = version + 1
WHERE status IN (0, 1, 2)
  AND plan_date <= DATE_SUB(CURDATE(), INTERVAL 1 DAY)
LIMIT 200;
```

**cron**：`0 30 2 * * *`，每天都跑（含周末，用于收尾周五遗留的脏数据）。

**为什么是 02:30 而不是 02:00**：打卡窗口在 02:00 关闭，留 30 分钟给"最后一秒提交"的请求落库，
避免打卡与过期任务抢同一行。

### 4.3 实现要点（四个 Job 通用）

- 所有 Job **复用 Service 方法**，不直接写 SQL 改状态——否则会漏掉通知、爱心值和 `version` 自增。
- `AutoCompleteJob` 必须复用 `PlanService.autoComplete(planId)`，保证与手动完成走同一条加分逻辑。
- 单次处理上限（如 200 条）分批跑，防止单次长事务锁表。
- 每个 Job 打一行汇总日志：`扫描 n 条，处理 m 条，失败 k 条`。
