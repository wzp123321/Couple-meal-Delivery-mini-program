> **Service**：`HistoryService` `ReportService`

> **前置必读**：`../00-全局约定.md`、`../01-通用机制.md`（状态语义）、`../后端-00-架构.md`
> **前端对应**：`前端.md`

## 1. 数据表

**本模块不拥有自己的表**，只读 `meal_plan` 及其子表。

| 表 | 读什么 | 走的索引 |
|---|---|---|
| `meal_plan` | 主查询 | `idx_meal_plan_couple_date(couple_id, plan_date, status)` |
| `meal_plan_item` | 列表菜品名（**快照**，不受菜单改名影响）；报告统计最爱菜 | 按 `plan_id` `IN` 批量 |
| `meal_checkin` | 是否已打卡；报告统计打卡天数 | `idx_meal_checkin_couple_time` |
| `love_value` | 报告里的爱心值增量 | `idx_love_value_couple_user(couple_id, user_id)` |

> 历史**包含全部状态**（4 已完成 / 5 已取消 / 6 已过期）。取消和过期也是记忆的一部分，
> 只是视觉上弱化，不做隐藏。

## 2. 接口契约

| 方法 | 路径 | 入参 | 出参 | 错误码 |
|---|---|---|---|---|
| GET | `/api/plan/history` | `pageNo`, `pageSize`, `status?`（0–6，可多选）, `role?`（`orderer`/`carrier`） | 分页列表 + 总数 | 1002 |
| GET | `/api/report` | `scope`（`month`/`year`）, `anchor`（`2026-09` / `2026`，缺省为上一自然月 / 当年） | 报告字段见 §3.4 | 1002 |

列表项字段（精简，不含详情）：

```json
{
  "id": 12,
  "planDate": "2026-10-27",
  "status": 4,
  "role": "orderer",
  "items": ["番茄炒蛋", "紫菜蛋花汤"],
  "partnerNickname": "小满",
  "checkinRating": 3,
  "hasCheckin": true
}
```

> **列表不返回 `actions[]`**。历史项多数是终态，不做操作；需要操作的去详情页。

## 3. 实现

### 3.1 查询

```sql
SELECT p.id, p.plan_date, p.status, p.orderer_id, p.carrier_id, ...
FROM meal_plan p
WHERE p.couple_id = #{ctx.coupleId}
  AND p.plan_date < CURDATE()        -- 今天的不进历史，避免与今日页重复
  <if status 非空> AND p.status IN (...) </if>
ORDER BY p.plan_date DESC, p.id DESC
LIMIT ?, ?
```

- **排序用 `plan_date DESC, id DESC`**，同一天多条也能稳定分页。
- `pageSize` 默认 20，上限 50。
- 菜品名用一次 `IN` 批量查 `meal_plan_item`，**不要 N+1**。

### 3.2 角色标注

`role` 由 `orderer_id == me ? 'orderer' : 'carrier'` 计算，前端据此决定文案
（「我点的」/「我带的」），不用传 `userId` 给前端自己比。

### 3.3 筛选

`status` 支持多选（如只看「已完成 + 已取消」）。空数组等同不筛。

### 3.4 报告（月报 / 年报）

`GET /api/report?scope=month&anchor=2026-09`（`anchor` 缺省：月报取上一自然月，年报取当年）

**统计口径统一为「已完成」（`status=4`）**。取消与过期不计入次数——否则"带饭次数"会被爽约拉高，
这也和爱心值「只有完成才加分」的口径一致。

| 字段 | 含义 |
|---|---|
| `planCount` | 期间内完成的约定数 |
| `carrierCount` | `{ me, partner }` 各自带了几次 |
| `topDishes` | 出现最多的 3 道菜 |
| `checkinDays` | 有打卡的天数（同一天多次只算一天） |
| `loveValueDelta` | 期间爱心值增量 |
| `longestStreak` | 最长连续带饭天数（**仅年报**） |

```sql
-- 双方各自带了几次
SELECT carrier_id, COUNT(*) AS cnt
FROM meal_plan
WHERE couple_id = #{coupleId} AND status = 4
  AND plan_date BETWEEN #{start} AND #{end}
GROUP BY carrier_id;

-- 最爱菜 top3
SELECT i.name, COUNT(*) AS cnt
FROM meal_plan_item i
JOIN meal_plan p ON p.id = i.plan_id
WHERE p.couple_id = #{coupleId} AND p.status = 4
  AND p.plan_date BETWEEN #{start} AND #{end}
GROUP BY i.name ORDER BY cnt DESC LIMIT 3;

-- 打卡天数（一天多次只算一天）
SELECT COUNT(DISTINCT p.plan_date)
FROM meal_checkin c JOIN meal_plan p ON p.id = c.plan_id
WHERE p.couple_id = #{coupleId}
  AND p.plan_date BETWEEN #{start} AND #{end};
```

**最长连续用 Java 算，不写 SQL**：取期间内 `status=4` 的 `DISTINCT plan_date` 升序集合，一次遍历求最长连续段。
相邻两日之间**只有周末被跳过时算连续**，中间夹着任何一个工作日没带饭就断。SQL 求连续要用窗口函数，
可读性差且难表达"周末不计"，不如在内存里跑一遍。

**空期间不造数据**：`planCount = 0` 直接返回空报告，前端不渲染卡片，也不拼一张"0 次"的统计——
那不是记忆，是报表。

## 5. 验收要点

对照 `openspec/changes/bootstrap-mvp/specs/plan-history/spec.md`：

- [ ] 只返回 `plan_date < 今天` 的约定（今天的在今日页）
- [ ] 包含已完成 / 已取消 / 已过期三种终态
- [ ] 按状态筛选、按角色筛选各自生效，可叠加
- [ ] 分页正确，同一天多条不重复不丢失
- [ ] 菜品名显示的是**约定时**的菜名（菜单后来改名不影响）
- [ ] 分页查询不产生 N+1
- [ ] 月报只统计「已完成」，取消/过期不计入带饭次数
- [ ] 上月无完成记录时返回 `planCount=0` 的空报告
- [ ] 年报最长连续：中间隔着周末算连续，中间隔着一个工作日没带饭则断
- [ ] 换过关系的历史不混入年报（按当前 `couple_id` 过滤）

## 6. 易错点

| 坑 | 说明 |
|---|---|
| 历史里带今天的约定 | 会与今日页重复，用户以为数据翻倍 |
| 菜品名 join `menu_item` | 菜单改名/删除后历史会变形。**读 `meal_plan_item.name` 快照** |
| 只查已完成 | 取消和过期也是历史，藏起来反而不真实 |
| 逐条查菜品 | 一页 20 条就是 20 次查询。**批量 `IN`** |
| 排序只用 `plan_date` | 同一天多条时分页会抖动，必须加 `id DESC` |
| 报告把取消/过期算进次数 | 统计口径必须只有 `status=4`，否则与爱心值口径打架 |
