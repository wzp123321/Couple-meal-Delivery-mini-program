## 1. 页面 → 接口

| 位置 | 调用 | 时机 |
|---|---|---|
| 打卡弹层 | `POST /api/checkin/upload` | 每选一张，逐张上传 |
| 打卡弹层 | `POST /api/checkin/submit` | 全部图片上传成功后提交 |
| 详情页打卡区 | `POST /api/checkin/update` | 打卡当天内修改评价/点评 |
| 详情页打卡区 | `POST /api/checkin/reply` | 带饭方回应 |
| `gallery` | `GET /api/checkin/gallery` | 进页 / 触底加载 |

## 2. 上传状态机（含单张重试）

```
uni.chooseMedia(count: 2 - 已选, sizeType: ['compressed'])
  → canvas 压缩：长边 1080、质量 0.8，压不到 ≤500KB 再降到 0.7
  → 逐张 POST /api/checkin/upload   ← 串行，不并发
      ├─ 成功 → 记录 { url, thumbUrl }，缩略图转正常态
      └─ 失败 → 该张标红 + 单张「重试」，不影响其他张
  → 全部成功 → POST /api/checkin/submit（只传 url 数组）
```

- 上传中禁止退出弹层（`loading-mask` 挡住）。
- **已传成功的图不重复上传**（PRD §12.7 明确要求）。
- 单张失败只重试那一张，不整单重来。
- **串行上传**：同一时刻只有 1 个 `uploadFile` 在跑，弱网下两个请求互抢反而都慢。

## 3. 打卡弹层

| 区块 | 要点 |
|---|---|
| 图片区 | 沿用 **3 宫格布局**（视觉不变），最多 **2 张**照片 + 1 个「+」格；两格满后「+」隐藏；可删除单张（仅未提交时） |
| 评价 | 三档大按钮：🔥香 / 😋好吃 / 😐还差点意思（**不用五星**，PRD Q6） |
| 点评 | 文本框 ≤100 字，实时计数 |
| 提交 | 全部图片成功才可点；`loading` 态防重复 |

## 4. 相册页（`pages/gallery`）

- 按月分组标题（「2026 年 10 月」），卡片瀑布流。
- **卡片与网格一律用 `thumbUrl`（320 长边）**，点开大图预览才用 `url`。
- 图片懒加载，点击进大图预览。
- 未过审的图**不展示也不占位**（后端已不返回），整条全屏蔽时该卡片只显示文字。
- 带饭方回应直接显示在卡片下方（≤50 字，一行截断）。

## 5. 验收要点

对照 `openspec/changes/bootstrap-mvp/specs/meal-checkin/spec.md`：

- [ ] 只有接收方在详情页看到打卡入口；带饭方看不到
- [ ] 选满 2 张后「+」隐藏，删除一张后恢复
- [ ] 上传拿到的 `{url, thumbUrl}` 都记录；相册卡片用 `thumbUrl`，点开预览才加载 `url`
- [ ] 两张图串行上传，不出现两个请求并发
- [ ] 某张上传失败只该张标红可重试，已成功的图不会重传
- [ ] 上传中点击遮罩无法关闭弹层
- [ ] 提交按钮在图片未全部成功前置灰
- [ ] 相册里被屏蔽的图不出现，整条全屏蔽时卡片仍显示文字与评分
- [ ] 打卡完成后入口变成「查看打卡」，没有删除按钮

## 6. 易错点

| 坑 | 说明 |
|---|---|
| 整单重传 | 用户已传成功的图再传一遍，既慢又可能重复占存储。**只重试失败那张** |
| 提交时不校验图片状态 | 有失败的图仍提交，后端因图片 URL 缺失报错。**全部成功才可点** |
| 相册卡片用原图 | 一屏 10 张 = 4MB，弱网直接卡住。**列表只用 `thumbUrl`，预览才取原图** |
| 前端压完就按 1080 判大小 | 前端压完仍可能超 500KB（微信 canvas 质量不可控），后端会再压一次；前端不要据此拒绝用户 |
| 前端只压缩不校验 | 后端仍会重编码，但前端压不到位会白等流量。压到长边 1080 / ≤500KB |
| 相册为被屏蔽图留空位 | 后端根本不返回，前端按「不占位」渲染，别写占位逻辑 |
| 提供删除打卡入口 | PRD 明确"不删只改"，删除属设置里的数据删除 |
