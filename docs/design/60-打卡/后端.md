> **OpenSpec**：`meal-checkin` · **里程碑** M6（最复杂的一条链路）
> **Service**：`CheckinService` `MediaAuditService` · **表**：`meal_checkin` `meal_checkin_image`
> **前置必读**：`../00-全局约定.md`、`../01-通用机制.md`、`../后端-00-架构.md`
> **前端对应**：`前端.md`

> **副作用指向**：提交后发通知 `type=6` → `../50-通知/后端.md`

## 1. 数据表

### `meal_checkin`（打卡主体）

| 字段 | 类型 | 说明 |
|---|---|---|
| `plan_id` | BIGINT | `uk_meal_checkin_plan` —— **一个约定只打一次卡** |
| `couple_id` | BIGINT | 关系隔离键 |
| `user_id` | BIGINT | 打卡人（必为接收方 = `orderer_id`） |
| `rating` | TINYINT NULL | `1` 还差点意思 / `2` 好吃 / `3` 香 |
| `content` | VARCHAR(255) NULL | 点评 **≤100 字** |
| `reply` | VARCHAR(128) NULL | 带饭方回应 **≤50 字** |
| `reply_by` / `reply_time` | — | 回应人与时间 |
| `audit_status` | TINYINT | **汇总态**：`0` 审核中 / `1` 全部通过 / `2` 含屏蔽图 |

索引 `idx_meal_checkin_couple_time(couple_id, create_time)` 服务相册按月倒序翻页。

### `meal_checkin_image`（审核粒度子表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `checkin_id` | BIGINT | 所属打卡 |
| `url` | VARCHAR(255) | **相对路径** `/upload/yyyyMM/x.jpg` |
| `seq` | TINYINT | 0–2，最多 3 张 |
| `audit_status` | TINYINT | `0` 审核中 / `1` 通过 / `2` 屏蔽 |
| `trace_id` | VARCHAR(64) NULL | 微信 `mediaCheckAsync` 返回的追踪号，`uk_meal_checkin_image_trace` |
| `audited_time` | DATETIME NULL | 回调时间 |

> **为什么必须拆表（D4）**：`mediaCheckAsync` 异步按 `trace_id` 回写**单张**结果。
> 若用 `images` 逗号串 + 单一 `audit_status`，3 张里坏 1 张只能整条屏蔽，用户会以为丢数据且无法恢复。

## 2. 接口契约

| 方法 | 路径 | 入参 | 出参 | 错误码 |
|---|---|---|---|---|
| POST | `/api/checkin/upload` | multipart 单张 | `url`（相对路径） | 4001, 4002, 5001 |
| POST | `/api/checkin/submit` | `planId`, `images[]`（1–3）, `rating`, `content` | `checkinId` | 3001, 3002, 3003, 3004, 3010 |
| POST | `/api/checkin/update` | `checkinId`, `rating`, `content` | — | 1002, 3003 |
| POST | `/api/checkin/reply` | `checkinId`, `reply`（≤50 字） | — | 1002 |
| GET | `/api/checkin/gallery` | `cursor`, `size` | 按月分组，**只返回已过审图片** | 1002 |
| POST | `/api/wx/media-check-callback` | 微信 POST `{trace_id, result, errcode}` | `{"errcode":0}` | **免 token** |

## 3. 实现

### 3.1 第一步：上传（`POST /api/checkin/upload`）

1. 类型白名单 `jpg/png/webp`，原始大小 ≤10MB，否则 `4001` / `4002`。
2. **重编码**：长边压到 1080，JPEG 质量 0.8，循环降质直到 ≤1MB。
3. **剥离 EXIF —— 必须做**。手机原图带 GPS，会把家庭住址泄露到服务器。
4. 落盘 `/data/upload/yyyyMM/{uuid}.jpg`，返回 `url`（相对路径，D12）。
5. 此步**不调审核**，只返回 URL。

> 前端也会压缩（省流量），但**后端不能只信前端**——重编码 + 剥 EXIF 必须自己做。

### 3.2 第二步：提交（`POST /api/checkin/submit`）

```
{ planId, images:["/upload/202610/abc.jpg", ...], rating, content }
```

前置校验：

| 校验 | 失败码 |
|---|---|
| `plan.orderer_id == me`（**只有接收方能打卡**） | `3004` |
| `plan.status ∈ {3,4}` | `3010` |
| 窗口：交付当天 **10:00** ~ **次日 02:00** | `3003 打卡时间已过` |
| `images` 1–3 张 | `3002` |
| `uk_meal_checkin_plan` 冲突 | `3001 这个约定已经打过卡了` |

> **窗口边界**：起点是交付当天 **10:00**（PRD §5.7 原文），不是 00:00 —— 早上 9 点交付的约定当时还不能打卡。
> 终点次日 02:00 与 `PlanExpireJob`（次日 02:30）错开 30 分钟，见 `../01-通用机制.md §4`。

事务内：

1. `insert meal_checkin`（`audit_status=0`）
2. 逐张调 `mediaCheckAsync(url, mediaType=2, version=2, scene=1)`
   - 成功 → 拿 `trace_id`，`insert meal_checkin_image(checkin_id, url, seq, audit_status=0, trace_id)`
   - **失败 → 仍插入图片行但 `trace_id=null`**，由补偿任务重试（不能因为审核接口挂了就丢照片）
3. 发通知 `type=6` 给带饭方

**打卡不额外加爱心值** —— 爱心值只在 `status 3→4` 时加一次（PRD Q6，见 `../40-爱心值/后端.md`）。

### 3.3 第三步：审核回调（`WxCallbackController`，**不走 token 拦截器**）

1. 微信 POST `{trace_id, result:{suggest, label}, errcode}`
2. 按 `uk_meal_checkin_image_trace` 定位图片 → `audit_status = (suggest == "pass") ? 1 : 2`
3. 重算 `meal_checkin.audit_status`：全通过 → `1`；含屏蔽 → `2`；仍有审核中 → `0`
4. 返回 `{"errcode": 0}`

回调无签名校验（微信机制如此），防护靠两点：**路径带随机段**、**只接受库里存在的 `trace_id`**。
重复推送安全：按 `trace_id` 定值 update，同值重复无副作用。

### 3.4 第四步：展示

- 相册与详情**只返回 `audit_status=1` 的图片**；`2` 的不返回，前端用占位说明"有图片未通过审核"。
- 若所有图片都被屏蔽，整条打卡不展示图片区，**文字与评分照常显示**。
- 相册按 `create_time` 倒序 + 游标分页，按自然月分组。

### 3.5 修改与回应

- `/api/checkin/update`：**打卡不删只改**（删了记忆就断，PRD 约定），仅限打卡当天。
- `/api/checkin/reply`：带饭方回应 ≤50 字，一条打卡只有一条回应（覆盖式更新）。

## 4. 定时任务

### 审核补偿

| 项 | 规则 |
|---|---|
| 触发 | `trace_id IS NULL` 且创建超过 5 分钟的图片行 |
| 动作 | 重新调 `mediaCheckAsync`，成功则回填 `trace_id` |
| 上限 | 单次 200 条，避免长事务 |

> 这个补偿是 §3.2「审核接口挂了仍存图」的配套。没有它，接口抖动期间的照片会永远停在"审核中"。

## 5. 验收要点

对照 `openspec/changes/bootstrap-mvp/specs/meal-checkin/spec.md`：

- [ ] 只有接收方（`orderer`）能打卡，带饭方打卡返回 3004
- [ ] `status` 不是 3/4 时返回 3010
- [ ] 交付当天 09:59 打卡 → 3003；10:01 → 成功
- [ ] 次日 02:01 打卡 → 3003；次日 02:29 仍可打（过期任务 02:30 才跑）
- [ ] 一约定只能打一次卡，重复提交 3001
- [ ] 图片必填 1–3 张，0 张或 4 张返回 3002
- [ ] 上传后原图 EXIF **不含 GPS**（用 `exiftool` 验证）
- [ ] 3 张图 1 张被封 → 相册只显示 2 张，另 1 张不出现且整条不隐藏
- [ ] 审核接口挂掉时照片仍入库，补偿任务能补上 `trace_id`
- [ ] **打卡不增加爱心值**

## 6. 易错点

| 坑 | 说明 |
|---|---|
| 打卡加爱心值 | PRD Q6 明确"不额外加"，加了就变成刷分 |
| 窗口起点写成 00:00 | PRD §5.7 是**当天 10:00**。写错会导致早上交付的约定立刻能打卡 |
| 忘记剥 EXIF | GPS 泄露家庭住址，是隐私事故 |
| 审核失败就不存图 | 审核接口抖动会丢用户照片。**先存行，`trace_id` 留空等补偿** |
| 用单一 `audit_status` 判断单张 | 必须按 `meal_checkin_image` 单张判断，聚合态只用于列表粗筛 |
| 未过审图片返回给前端 | 前端只是"不显示"，URL 仍在网络上可访问。**后端不得返回** |
| 打卡支持删除 | PRD 明确"不删只改"，删了记忆就断；真删走设置里的数据删除 |
| 回调走 token 拦截器 | 微信不会带 token，会被 401 拦掉。**必须免鉴权** |
| 回调路径可枚举 | 无签名校验，必须给路径加随机段，并只认库里存在的 `trace_id` |
