# 50 通知 · 后端

> **OpenSpec**：`notifications` · **里程碑** M4
> **Service**：`NotifyService` · **表**：`notification`
> **前置必读**：`../00-全局约定.md`、`../01-通用机制.md`、`../后端-00-架构.md`
> **前端对应**：`前端.md`
> **MVP 范围**：仅站内红点/角标。**不做微信订阅消息**（二期）

---

## 1. 数据表

### `notification`

| 字段 | 类型 | 说明 |
|---|---|---|
| `couple_id` | BIGINT | 关系隔离键 |
| `receiver_id` | BIGINT | 收件人 |
| `plan_id` | BIGINT NULL | 关联约定；**每日提醒为 NULL** |
| `type` | TINYINT | `1`新约定 `2`被认领 `3`已送达 `4`已完成 `5`每日提醒 `6`已打卡 |
| `title` / `content` | VARCHAR(64) / VARCHAR(255) | 文案 |
| `read_flag` / `read_time` | — | 已读状态 |

**三条索引**：

| 索引 | 作用 |
|---|---|
| `uk_notification_plan_type_receiver(plan_id, type, receiver_id)` | 同约定同类型只发一次（**去重核心**） |
| `idx_notification_receiver_read(receiver_id, read_flag, create_time)` | 未读数 + 列表 |
| `idx_notification_receiver_type_time(receiver_id, type, create_time)` | `DailyRemindJob`：当天是否已提醒过 |

> MySQL 唯一索引对 `NULL` 不去重 —— `plan_id` 为 NULL 的每日提醒**天然不受该约束**，正好符合需求。

## 2. 接口契约

| 方法 | 路径 | 入参 | 出参 | 错误码 |
|---|---|---|---|---|
| GET | `/api/msg/list` | `pageNo`, `pageSize` | 分页列表 | 1002 |
| GET | `/api/msg/unread` | — | `{ unread }` | 1002 |
| POST | `/api/msg/read` | — | — | 1002 |

`/api/msg/read` 是**全部已读**（进列表即清），不做单条已读。

## 3. 实现

### 3.1 唯一写入入口

```java
@Transactional
public void push(Long coupleId, Long receiverId, Long planId,
                 int type, String title, String content) {
    try {
        notificationMapper.insert(...);
    } catch (DuplicateKeyException e) {
        // uk_notification_plan_type_receiver 拦截 = 已发过，静默忽略
    }
}
```

**为什么 catch 而不先查**：与爱心值同理，并发下先查必漏判（见 `../01-通用机制.md §2` 原则 1）。

### 3.2 通知类型与触发点

| type | 触发 | 收件人 | 文案方向 |
|---|---|---|---|
| 1 新约定 | 发起约定（`../20-约定/后端.md §3.1`） | 非发起方 | 「TA 想吃…」 |
| 2 被认领 | 认领 / 改派（`../20-约定/后端.md §3.2`） | 点餐方 | 「TA 接单啦」 |
| 3 已送达 | 送达（`../20-约定/后端.md §3.4`） | 点餐方 | 「饭已经放到…」 |
| 4 已完成 | 完成 / 自动完成（`../20-约定/后端.md §3.5`、`§4.1`） | 带饭方 | 「这顿饭记下了」 |
| 5 每日提醒 | `DailyRemindJob` | 带饭方 | 「今天还没人认领哦」 |
| 6 已打卡 | 提交打卡（`../60-打卡/后端.md §3.2`） | 带饭方 | 「TA 给这顿饭打了分」 |

**文案基调**：情感化，不用「订单」「配送」「下单」等交易词汇（PRD §12.11）。
文案集中在一处常量类，不散落在各 Service 里。

### 3.3 服务端不做的事

- **不维护未读数缓存**。`count(*) where receiver_id=? and read_flag=0` 走 `idx_notification_receiver_read`，量小够用。
- **不做推送通道**。红点靠前端进页面时拉取。

## 4. 定时任务

### `DailyRemindJob`

| 项 | 规则 |
|---|---|
| cron | `0 0 11 * * MON-FRI`（工作日 11:00） |
| 条件 | `status=0 and plan_date=今天` |
| 动作 | 发 `type=5` 通知给**带饭方**（即非 orderer 一方） |
| 去重 | 当天是否已有 `type=5` 记录（用 `idx_notification_receiver_type_time`），有则跳过 |

> PRD §12.6：11:00 未认领催一次，**只催一次**。

---

## 5. 验收要点

对照 `openspec/changes/bootstrap-mvp/specs/notifications/spec.md`：

- [ ] 六类通知在对应动作后各产生一条
- [ ] 同一约定同一类型重复触发（如重复送达）只留一条
- [ ] 每日提醒当天只发一次，且只发给带饭方
- [ ] 未读数只统计 `read_flag=0` 且属于当前用户
- [ ] 解绑后再绑定到另一人，**看不到上一段关系的通知**

## 6. 易错点

| 坑 | 说明 |
|---|---|
| 先查再插 | 并发下红点跳数。**靠 `uk_notification_plan_type_receiver` + catch** |
| 每日提醒用 `plan_id` 去重 | 每日提醒 `plan_id` 为 NULL，唯一索引不生效，必须另用"当天是否已有 type=5"判断 |
| 未读数做成缓存 | 多一次写就多一个不一致点，量小直接 `count(*)` |
| 解绑后通知串号 | 查询必须带 `couple_id = ctx.coupleId`，不能只按 `receiver_id` |
| 文案写死在各 Service | 改一句文案要翻遍代码，集中到常量类 |
