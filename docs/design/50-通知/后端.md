# 50 通知 · 后端

> **OpenSpec**：`notifications` · **里程碑** M4
> **Service**：`NotifyService` · **表**：`notification`
> **前置必读**：`../00-全局约定.md`、`../01-通用机制.md`、`../后端-00-架构.md`
> **前端对应**：`前端.md`
> **范围**：站内红点/角标 + 微信订阅消息旁路通道（见 §3.4），站内信始终是可靠通道

---

## 1. 数据表

### `notification`

| 字段 | 类型 | 说明 |
|---|---|---|
| `couple_id` | BIGINT | 关系隔离键 |
| `receiver_id` | BIGINT | 收件人 |
| `plan_id` | BIGINT NULL | 关联约定；每日提醒也带约定的 `plan_id`（见 §4） |
| `type` | TINYINT | `1`新约定 `2`被认领 `3`已送达 `4`已完成 `5`每日提醒 `6`已打卡 |
| `title` / `content` | VARCHAR(64) / VARCHAR(255) | 文案 |
| `read_flag` / `read_time` | — | 已读状态 |

**三条索引**：

| 索引 | 作用 |
|---|---|
| `uk_notification_plan_type_receiver(plan_id, type, receiver_id)` | 同约定同类型只发一次（**去重核心**） |
| `idx_notification_receiver_read(receiver_id, read_flag, create_time)` | 未读数 + 列表 |
| `idx_notification_receiver_type_time(receiver_id, type, create_time)` | 按类型取最近通知（排查 / 运营查询） |

> MySQL 唯一索引对 `NULL` 不去重 —— 因此每日提醒也携带 `plan_id`，让 `uk_notification_plan_type_receiver` 直接覆盖它，无需另做「先查再插」。

## 2. 接口契约

| 方法 | 路径 | 入参 | 出参 | 错误码 |
|---|---|---|---|---|
| GET | `/api/msg/list` | `pageNo`, `pageSize` | 分页列表 | 1002 |
| GET | `/api/msg/unread` | — | `{ unread }` | 1002 |
| POST | `/api/msg/read` | — | — | 1002 |

`/api/msg/read` 是**全部已读**（进列表即清），不做单条已读。

## 3. 实现

### 3.1 唯一写入入口

```java
@Transactional
public void push(Long coupleId, Long receiverId, Long planId,
                 int type, String title, String content) {
    try {
        notificationMapper.insert(...);
    } catch (DuplicateKeyException e) {
        // uk_notification_plan_type_receiver 拦截 = 已发过，静默忽略
    }
}
```

**为什么 catch 而不先查**：与爱心值同理，并发下先查必漏判（见 `../01-通用机制.md §2` 原则 1）。

### 3.2 通知类型与触发点

| type | 触发 | 收件人 | 文案方向 |
|---|---|---|---|
| 1 新约定 | 发起约定（`../20-约定/后端.md §3.1`） | 非发起方 | 「TA 想吃…」 |
| 2 被认领 | 认领 / 改派（`../20-约定/后端.md §3.2`） | 点餐方 | 「TA 接单啦」 |
| 3 已送达 | 送达（`../20-约定/后端.md §3.4`） | 点餐方 | 「饭已经放到…」 |
| 4 已完成 | 完成 / 自动完成（`../20-约定/后端.md §3.5`、`§4.1`） | 带饭方 | 「这顿饭记下了」 |
| 5 每日提醒 | `DailyRemindJob`（午饭 11:00 / 晚饭 17:00） | 带饭方 | 「今天午饭谁带呀」/「今天晚饭谁带呀」 |
| 6 已打卡 | 提交打卡（`../60-打卡/后端.md §3.2`） | 带饭方 | 「TA 给这顿饭打了分」 |

**文案基调**：情感化，不用「订单」「配送」「下单」等交易词汇（PRD §12.11）。
文案集中在一处常量类，不散落在各 Service 里。

### 3.3 服务端不做的事

- **不维护未读数缓存**。`count(*) where receiver_id=? and read_flag=0` 走 `idx_notification_receiver_read`，量小够用。
- **站内通知是唯一可靠通道**。微信订阅消息只是增量旁路：模板未配 / 用户未授权 / 微信报错一律只记日志，站内行照常写入（见 §3.4）。

### 3.4 微信订阅消息（旁路通道）

`NotifyServiceImpl.push` 写完站内行后调 `SubscribeMessageService.send`，由它决定发不发：

| 项 | 规则 |
|---|---|
| 覆盖事件 | 只有 `CLAIMED`（被认领）、`DELIVERED`（已送达）、`CHECKIN_REMIND`（待打卡）三类；其余类型只写站内信 |
| 模板 ID | `couple-meal.wx.tpl-*` 配置；未配置则该事件直接跳过 |
| access_token | `WxConfig` 进程内缓存，提前 60 秒刷新，获取失败不阻断主流程 |
| 失败策略 | 任何异常只记日志（用户未授权 / 模板失效 / 网络错误），绝不回滚已写入的站内行 |
| 前端职责 | 只负责 `uni.requestSubscribeMessage` 申请授权；`GET /api/subscribe/templates` 返回三键模板 ID，空串表示未配置，前端静默跳过 |

> 一次性订阅语义：用户每授权一次只能收一条，因此前端在「创建约定成功 / 认领成功」后各静默补授权一次。

## 4. 定时任务

### `DailyRemindJob`

| 项 | 规则 |
|---|---|
| cron | 午饭 `daily-remind-cron`（工作日 11:00）、晚饭 `daily-remind-dinner-cron`（工作日 17:00，给 18:00 截止留一小时） |
| 条件 | `status=0 and plan_date=今天 and meal_type=当前餐段` |
| 开关 | `couple.remind_enabled=0` 的关系整条跳过（设置页可关，不影响其他事件通知） |
| 动作 | 发 `type=5` 通知给**带饭方**（非 orderer 一方），文案按餐段：「今天午饭谁带呀」/「今天晚饭谁带呀」 |
| 去重 | 通知携带 `plan_id`，由 `uk_notification_plan_type_receiver` 兜底：同一约定同一人只一条，午饭/晚饭互不干扰 |

> PRD §12.6：每个餐段未认领催一次，**只催一次**。
> 关系数据按 `coupleId` 批量查一次（`IN`），不逐条 `selectById`。

## 5. 验收要点

对照 `openspec/changes/bootstrap-mvp/specs/notifications/spec.md`：

- [ ] 六类通知在对应动作后各产生一条
- [ ] 同一约定同一类型重复触发（如重复送达）只留一条
- [ ] 每日提醒每个餐段只发一次，且只发给带饭方
- [ ] `remind_enabled=0` 的关系不发每日提醒，但认领/送达等事件通知照常
- [ ] 未读数只统计 `read_flag=0` 且属于当前用户
- [ ] 解绑后再绑定到另一人，**看不到上一段关系的通知**

## 6. 易错点

| 坑 | 说明 |
|---|---|
| 先查再插 | 并发下红点跳数。**靠 `uk_notification_plan_type_receiver` + catch** |
| 每日提醒手工 count 去重 | `plan_id` 留 NULL 就只能「先查再插」，并发必漏判；带上 `plan_id` 交给唯一索引 |
| 提醒不看开关 | `remind_enabled=0` 仍发提醒，用户会认为开关是摆设；查到约定后必须按关系过滤 |
| 未读数做成缓存 | 多一次写就多一个不一致点，量小直接 `count(*)` |
| 解绑后通知串号 | 查询必须带 `couple_id = ctx.coupleId`，不能只按 `receiver_id` |
| 文案写死在各 Service | 改一句文案要翻遍代码，集中到常量类 |
