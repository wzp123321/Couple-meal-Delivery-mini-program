## 1. 数据表

### `meal_plan`（核心表）

| 字段 | 类型 | 说明 |
|---|---|---|
| `couple_id` | BIGINT | 关系隔离键，**只从会话取** |
| `orderer_id` | BIGINT | 点餐方（想吃什么的人） |
| `carrier_id` | BIGINT NULL | 带饭方（认领后写入 / 主动带时直接写入） |
| `meal_type` | TINYINT | `1` 午饭 / `2` 晚饭 |
| `source` | TINYINT | `0` 点餐 / `1` 主动带 |
| `status` | TINYINT | `0`待认领 `1`待接收 `2`备餐中 `3`已交付 `4`已完成 `5`已取消 `6`已过期 |
| `plan_date` | DATE | 约定日期（工作日） |
| `remark` | VARCHAR(512) | 口味/时间/忌口备注，**≤100 字** |
| `deliver_location` | VARCHAR(64) | 交付位置：前台/工位/门口 |
| `deliver_note` | VARCHAR(128) | 便签留言，**≤80 字** |
| `claimed_time` / `delivered_time` / `completed_time` / `cancelled_time` | DATETIME | 各阶段时间戳，`delivered_time` 是 24h 自动完成的基准 |
| `version` | INT | 乐观锁，防双端并发改状态 |

**五条索引各有专职**：

| 索引 | 服务的查询 |
|---|---|
| `idx_meal_plan_couple_date(couple_id, plan_date, status)` | 今日约定 / 周历 / 历史筛选（三处共用） |
| `idx_meal_plan_carrier(carrier_id, status)` | 「我带的饭」列表 |
| `idx_meal_plan_orderer(orderer_id, status)` | 「我点的饭」列表 |
| `idx_meal_plan_status_delivered(status, delivered_time)` | `AutoCompleteJob` |
| `idx_meal_plan_status_date(status, plan_date)` | `PlanExpireJob` |

### `meal_plan_item`（菜品快照）

| 字段 | 说明 |
|---|---|
| `plan_id` | 所属约定 |
| `menu_item_id` | 来源菜品，**手输菜名为 NULL** |
| `name` | 菜名快照 —— 菜单改名/删除后，历史仍显示当时名字（D2） |
| `seq` | 排序 0–9（1–10 道） |

> 两条索引：`idx_meal_plan_item_plan(plan_id, seq)` 取明细；`idx_meal_plan_item_menu(menu_item_id)` 供菜单库的「最近点过」排序反查（见 `../30-菜单与偏好/后端.md §3.2`）。

### `cancel_log`

| 字段 | 说明 |
|---|---|
| `couple_id` | 关系隔离，所有业务查询必带 |
| `plan_id` | `uk_cancel_log_plan` —— 一个约定只记一次取消 |
| `operator_id` | 谁取消的 |
| `reason` | 必填，业务 ≤100 字（列宽 255） |

> 取消不发爱心值，但没有记录就无法复盘（PRD 的"防错账"要求）。

## 2. 接口契约

| 方法 | 路径 | 入参 | 出参 | 错误码 |
|---|---|---|---|---|
| POST | `/api/plan/create` | `mealType`, `source`, `planDate`, `items:[{menuItemId?,name}]`, `remark` | `planId`, `warnings:[{name,avoidLevel}]` | 1009, 1010, 1011, 2003, 2004, 2005 |
| GET | `/api/plan/{id}` | — | 详情 + `items` + **当前用户可执行动作** `actions[]` | 1002, 1004 |
| POST | `/api/plan/{id}/claim` | — | — | 1002, 1004, 1005 |
| POST | `/api/plan/{id}/withdraw` | — | — | 1002, 1004 |
| POST | `/api/plan/{id}/confirm` | — | — | 1002, 1004 |

| POST | `/api/plan/{id}/deliver` | `deliverLocation`, `deliverNote` | — | 1002, 1004 |
| POST | `/api/plan/{id}/complete` | — | `loveValue` | 1002, 1004 |

## 3. 实现

### 3.1 发起约定

```
POST /api/plan/create
{ mealType, source, planDate, items:[{menuItemId?, name}], remark }
```

校验顺序（先便宜后贵，报错信息要具体）：

| 校验 | 失败码 |
|---|---|
| `planDate` 是工作日（周一至周五） | `1009 只能约工作日` |
| `planDate` ∈ `[today, today+7]` | `1011 日期超出可约范围` |
| 当日且 `now > 18:00` | `1010 今天太晚了，约明天吧` |
| `items` 数量 1–10，`name` ≤20 字 | `2003` / `2004` |
| `remark` ≤100 字 | `2005` |

**忌口不拦截**：命中 `avoid_level >= 2` 的菜品时照常写入，只在响应里返回
`warnings: [{name, avoidLevel}]`，前端弹强提醒让用户二次确认（PRD Q2 已拍板"只提醒不硬拦"）。

- `source=0`（点餐）：`orderer=me, carrier=null, status=0`
- `source=1`（主动带）：`orderer=对方, carrier=me, status=1`（已认领态，等对方确认）

写入 `meal_plan` + 批量 `meal_plan_item`（菜名快照），发通知 `type=1`。

### 3.2 认领 / 撤回

**认领** `POST /api/plan/{id}/claim`

```sql
UPDATE meal_plan
SET carrier_id = ?, status = 2, claimed_time = NOW(), version = version + 1
WHERE id = ? AND status = 0 AND source = 0 AND version = ?
```

- 前置校验：`orderer_id == me` → `1005`（不能认领自己点的）
- `affected rows = 0` → `1004 状态已变化`（被并发抢走或已被取消）
- **认领一步到位进「备餐中」**，不再经过「待接收」（D15）；「待接收」只属于主动带
- 成功后通知 `type=2` 给点餐方

**撤回** `POST /api/plan/{id}/withdraw` —— 带饭方把已认领的约定退回待认领

```sql
UPDATE meal_plan SET carrier_id = NULL, status = 0, claimed_time = NULL, version = version + 1
WHERE id = ? AND status = 2 AND source = 0 AND carrier_id = ?
```

撤回是退回待认领，**不是取消**，不写 `cancel_log`、不发爱心值。主动带（`source=1`）没有"待认领"可回，只能走 `cancel`。

### 3.3 确认 / 婉拒

- **确认**：`orderer=me` 且 `status=1` → `status=2`，通知带饭方"可以开始做啦"。
- **婉拒**：`orderer=me` 且 `status=1` → 走取消流程（`status=5` + `cancel_log.reason='婉拒'`），
  文案要比"取消"柔和（PRD §12.11 文案调性，属前端职责）。

### 3.4 送达

`POST /api/plan/{id}/deliver { deliverLocation, deliverNote }`

- 仅 `carrier=me` 且 `status=2`
- `deliverNote` ≤80 字
- `status=3, delivered_time=now`，通知 `type=3` 给点餐方

### 3.5 完成（触发爱心值）

`POST /api/plan/{id}/complete` —— 事务内两步

```java
// 1. 状态（条件更新，防重复点）
int n = planMapper.updateStatus(id, from=3, to=4, completedAt=now);
if (n == 0) throw new BizException(ErrorCode.STATUS_CONFLICT);

// 2. 爱心值（唯一索引兜底，重复当成功）—— 详见 40-爱心值/后端.md §3
loveValueService.award(coupleId, plan.carrierId, id);
```

**先改状态再加分**：状态更新失败时不会留下孤立爱心值；爱心值插入失败（重复）时状态已改，
符合"只加一次"的语义。

### 3.6 取消

`POST /api/plan/{id}/cancel { reason }`

- `reason` 必填，≤100 字 → 否则 `2006`
- 允许 `status ∈ {0,1,2}`；**已交付起不可取消**（饭已送到，只能领取或等 24h 自动完成），`status ∈ {3,4}` 一律 `1004`
- 条件更新 `status=5, cancelled_time=now`，随后 `insert cancel_log`
- `uk_cancel_log_plan` 冲突 → `1004`（已取消过）
- **不发爱心值**，通知对方

### 3.7 改派

`POST /api/plan/{id}/reassign { carrierId }` —— 仅带饭方，且 `status ∈ {1,2}`。
改的是"这顿饭由谁带"，不改变 `orderer`，不发通知类型以外的副作用（沿用 `type=2`）。

### 3.8 详情返回可执行动作

`GET /api/plan/{id}` 必须返回 `actions[]`，由 `PlanStateMachine` 按 `(status, 我的角色)` 计算，
**不让前端自己推**。前端只按 `actions[]` 决定按钮显隐，这是前后端唯一的状态判定来源。

## 4. 定时任务

### 4.1 `AutoCompleteJob`

| 项 | 规则 |
|---|---|
| cron | `0 0 * * * *`（每小时） |
| 条件 | `status=3 and delivered_time < now()-24h` |
| 动作 | → `status=4`，**照发爱心值** |

必须复用 `PlanService.autoComplete(planId)`，保证与手动完成走同一条加分逻辑（见 `../01-通用机制.md §4`）。

### 4.2 `PlanExpireJob`

cron `0 30 2 * * *`，规则见 `../01-通用机制.md §4`（次日 02:30、仅 0/1/2 状态）。

## 5. 验收要点

对照 `openspec/changes/bootstrap-mvp/specs/meal-plan/spec.md`：

- [ ] 周末发起约定返回 1009；超过 +7 天返回 1011
- [ ] 工作日 18:00 后发起当日返回 1010
- [ ] 点餐方点「我来带」返回 1005
- [ ] 两人同时认领，只有一人成功，另一人 1004
- [ ] 撤回后退回 `status=0`，**不产生 `cancel_log`**
- [ ] 完成时爱心值只加一次（重复点、并发点均只 +1）
- [ ] 取消必须带 reason，否则 2006；重复取消返回 1004
- [ ] **次日 02:30 后**，昨日 `status ∈ {0,1,2}` 转 6；`status=3` 不转
- [ ] 已交付超 24h 自动转 4 并加分
- [ ] 忌口命中只回 `warnings`，不阻断提交
- [ ] `GET /api/plan/{id}` 的 `actions[]` 与 PRD §12.4 权限矩阵逐格一致

## 6. 易错点

| 坑 | 说明 |
|---|---|
| Controller 收 `status` 入参 | 前端可传任意状态，状态机形同虚设。**只走具体动作**（D8） |
| 用 `select` 判断状态后 `update` | 并发下必漏判。**条件 UPDATE + affected rows**（D9） |
| 撤回写成取消 | 撤回要退回 `status=0` 且**不写 `cancel_log`**，两者语义不同 |
| 菜单改名影响历史 | 必须存 `meal_plan_item.name` 快照，不能 join 菜单表现取 |
| 完成时先加分再改状态 | 状态失败会留孤立爱心值。**先状态后加分** |
| `deliverNote` 存进 `remark` | 两个字段语义不同，`remark` 是点餐方写的备注 |
| `actions[]` 漏算角色 | 只按 `status` 算会把"点餐方的按钮"给带饭方看。必须带 `(status, 我的角色)` 二维判断 |
