## 1. 数据表

### `user`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT PK | 53bit 雪花 ID（D1，禁自增） |
| `openid` | VARCHAR(64) | 微信 openid，**登录唯一身份**，`uk_user_openid` |
| `nickname` | VARCHAR(64) NULL | 用户自行填写（`type="nickname"` 填写能力） |
| `avatar` | VARCHAR(255) NULL | 头像 URL |

### `couple`

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_a` / `user_b` | BIGINT | 规范化：`user_a < user_b`，`CHECK(user_a<user_b)` |
| `nickname_a` / `nickname_b` | VARCHAR(32) NULL | 各自的专属称呼 |
| `anniversary` | DATE NULL | 纪念日 |
| `theme` | VARCHAR(16) | 默认 `cream` |
| `status` | TINYINT | `1` 有效 / `0` 已解绑 |
| `unbound_time` | DATETIME NULL | 解绑时间 |

约束：`uk_couple_pair(user_a, user_b)` —— 同一对只可能有一条记录（含已解绑的）。

### `couple_invite`

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | CHAR(6) | 6 位纯数字，`uk_couple_invite_code` |
| `creator_id` | BIGINT | 发起方 |
| `status` | TINYINT | `0` 待使用 / `1` 已使用 / `2` 已过期 / `3` 已作废 |
| `expire_time` | DATETIME | = 创建 + 24h |
| `used_by` / `used_time` | — | 使用时回填 |

索引 `idx_couple_invite_creator_time(creator_id, create_time)` 专为限频统计而建。

## 2. 接口契约

| 方法 | 路径 | 入参 | 出参 | 错误码 |
|---|---|---|---|---|
| POST | `/api/auth/login` | `code`, `agreedPrivacy` | `token`, `userId`, `nickname`, `avatar`, `hasCouple` | 1001, 5001 |
| POST | `/api/couple/invite` | — | `code`, `expireAt` | 1006, 1007 |
| POST | `/api/couple/join` | `code` | `coupleId`, `partner` | 1003, 1007, 1008 |
| GET | `/api/couple/info` | — | 双方头像昵称、称呼、在一起天数、双方爱心值、`coupleId` | 1002 |
| POST | `/api/couple/settings` | `nicknameMine`, `anniversary`, `theme`, `remindEnabled` | — | 1002 |
| POST | `/api/couple/unbind` | `confirm` | — | 1002 |
| POST | `/api/user/delete` | — | — | 1001 |

> `login` 免鉴权；其余全部走 `AuthInterceptor`。所有接口**不接受** `coupleId` 入参（见 `../00-全局约定.md §4`）。

## 3. 实现

### 3.1 登录

```
POST /api/auth/login   { code, agreedPrivacy }
```

1. `agreedPrivacy != true` → 直接拒绝 `1001`（PRD §5.1 未同意不得登录）。
2. 调 `jscode2session` 换 `openid`。**`session_key` 不落库**——本项目不解密用户数据，用不到。
3. 按 `openid` 查 `user`，无则插入。
4. 签发 JWT：payload `{uid, exp}`，HS256，有效期 30 天。**不放 `coupleId`**——关系随时可绑可解，放进去会导致解绑后 token 仍带旧关系。
5. 返回 `{token, userId, nickname, avatar, hasCouple}`。

> 头像昵称走小程序头像昵称填写能力（`<button open-type="chooseAvatar">` + `<input type="nickname">`），
> `getUserProfile` 已废弃，不再使用。

### 3.2 生成邀请码

`POST /api/couple/invite`

1. 已有 `status=1` 的关系 → `1007 已有情侣关系`。
2. 限频：近 1 小时生成 ≥5 次 → `1006`（用 `idx_couple_invite_creator_time` 统计）。
3. `SecureRandom` 生成 6 位数字，插入；`uk_couple_invite_code` 冲突则重试，最多 5 次。
4. `expire_time = now + 24h`。

### 3.3 加入（全程一个事务）

`POST /api/couple/join`

1. `select ... for update` 锁住该码（防两人同时用同一码）。
2. 校验 `status=0` 且 `expire_time > now`，否则 `1003`。
3. `creator_id == me` → `1008 不能和自己绑定`。
4. 双方都不存在 `status=1` 的关系，否则 `1007`。
5. `user_a = min(me, creator)`，`user_b = max(...)`。
6. 查 `uk_couple_pair`：**已存在历史记录则复活**（`status=1, unbound_time=null`），否则 insert（D6）。
7. 码置 `status=1, used_by=me, used_time=now`。

### 3.4 解绑

逻辑删除：`couple.status=0, unbound_time=now`。**记录保留**，双方本地历史仍可查看。
解绑后 `GET /api/couple/info` 返回 `1002`，前端 `reLaunch` 到配对页。

### 3.5 账号注销（真实删除）

PRD §13 第 3 条是合规 P0：**逻辑删除不满足「删除权」**，个人身份数据必须真删。

| 数据 | 处理 | 理由 |
|---|---|---|
| `user` 行（`openid` / `nickname` / `avatar`） | **物理 `DELETE`** | `openid` 就是身份标识，留着等于没删 |
| 头像文件 | 删磁盘文件 | 防止"库里没了、URL 还能访问" |
| 本人上传的打卡图片 | 删 `meal_checkin_image` 行 + 磁盘文件 | 照片属个人信息，可能含本人肖像与住处 |
| `couple` | `status=0, unbound_time=now` | 另一方还要看自己的历史，不能连带清空 |
| 约定 / 爱心值 / 打卡文本 / 通知 | 保留，用户侧展示为「已注销用户」 | 对方的历史与爱心值不该因一方注销归零；此时已无身份标识 |
| 本人未使用的邀请码 | `status=3` 作废 | 防注销后码还能绑上 |

**执行顺序**（一个事务，先库后文件）：

1. 存在 `status=1` 的关系 → 先按 §3.4 解绑。
2. 删 `meal_checkin` 中 `user_id=me` 的图片行，收集待删文件路径。
3. 作废本人未使用的邀请码。
4. `DELETE FROM user WHERE id = ?`。
5. **事务提交后**删文件；单张失败只记 `WARN`，不回滚（文件删除幂等，可补脚本，不能因 IO 失败让用户注销不掉）。

**注销后 token 立即失效**：`AuthInterceptor` 解析 token 后按 `uid` 主键查 `user`，查不到返回 `1001`。
这一次主键查询成本可接受，顺带堵住"token 只带 uid、用户已删仍能访问"的漏洞。

**二次确认在前端**：服务端不设 `confirm` 参数——交互拦截由前端做，服务端只保证鉴权正确。

## 5. 验收要点

对照 `openspec/changes/bootstrap-mvp/specs/couple-binding/spec.md`：

- [ ] `agreedPrivacy != true` 调用登录返回 1001
- [ ] 6 位码 24h 有效、一次性；重复使用返回 1003
- [ ] 自己用自己生成的码返回 1008
- [ ] 双方任一已有有效关系返回 1007
- [ ] 解绑后记录保留（`status=0`），历史仍可查
- [ ] 解绑后再用同一对用户绑定 → **复活原记录**，不报 `uk_couple_pair` 冲突
- [ ] 1 小时内第 6 次生成邀请码返回 1006
- [ ] 注销后 `user` 行物理不存在，旧 token 访问任意接口返回 1001
- [ ] 注销后本人打卡照片（行 + 文件）已删除，对方历史仍在且显示「已注销用户」

## 6. 易错点

| 坑 | 说明 |
|---|---|
| token 里放 `coupleId` | 解绑后 token 仍带旧关系，会导致越权读到别人数据。**只放 `uid`** |
| 绑定时直接 insert | `uk_couple_pair` 对上已解绑的记录会冲突。**必须先查历史记录决定 update / insert**（D6） |
| 忘记规范化 `user_a < user_b` | 两人分别绑定时顺序不同会产生两条关系。`CHECK` 会在插入时报错，但更好的是应用层先排序 |
| 邀请码冲突直接抛异常 | `uk_couple_invite_code` 是 6 位数字空间，撞码正常，**应重试最多 5 次** |
| 注销时先删文件后提交事务 | 事务回滚了文件却删了，用户数据还在但照片没了。**必须先库后文件** |
