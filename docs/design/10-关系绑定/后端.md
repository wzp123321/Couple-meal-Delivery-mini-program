## 1. 数据表

### `user`

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT PK | 53bit 雪花 ID（D1，禁自增） |
| `openid` | VARCHAR(64) | 微信 openid，**登录唯一身份**，`uk_user_openid` |
| `nickname` | VARCHAR(64) NULL | 用户自行填写（`type="nickname"` 填写能力） |
| `avatar` | VARCHAR(255) NULL | 头像**相对路径** `/upload/avatar/{userId}_{ts}.jpg`，不存完整 URL（D12 / D16） |

### `couple`

| 字段 | 类型 | 说明 |
|---|---|---|
| `user_a` / `user_b` | BIGINT | 规范化：`user_a < user_b`，`CHECK(user_a<user_b)` |
| `nickname_a` / `nickname_b` | VARCHAR(32) NULL | 各自的专属称呼 |
| `anniversary` | DATE NULL | 纪念日 |
| `theme` | VARCHAR(16) | 默认 `cream` |
| `status` | TINYINT | `1` 有效 / `0` 已解绑 |
| `unbound_time` | DATETIME NULL | 解绑时间 |

约束：`uk_couple_pair(user_a, user_b)` —— 同一对只可能有一条记录（含已解绑的）。

### `couple_invite`

| 字段 | 类型 | 说明 |
|---|---|---|
| `code` | CHAR(6) | 6 位纯数字，`uk_couple_invite_code` |
| `creator_id` | BIGINT | 发起方 |
| `status` | TINYINT | `0` 待使用 / `1` 已使用 / `2` 已过期 / `3` 已作废 |
| `expire_time` | DATETIME | = 创建 + 24h |
| `used_by` / `used_time` | — | 使用时回填 |

索引 `idx_couple_invite_creator_time(creator_id, create_time)` 专为限频统计而建。

## 2. 接口契约

| 方法 | 路径 | 入参 | 出参 | 错误码 |
|---|---|---|---|---|
| POST | `/api/auth/login` | `code`, `agreedPrivacy` | `token`, `userId`, `nickname`, `avatar`, `hasCouple` | 1001, 5001 |
| POST | `/api/user/avatar` | multipart 单张 | `{ avatar }`（相对路径） | 4001, 4002, 4003, 5001 |
| POST | `/api/user/profile` | `nickname?`, `avatar?`（至少传一个） | `{ nickname, avatar }` | 1001, 1012, 4003, 4004 |
| POST | `/api/couple/invite` | — | `code`, `expireAt` | 1006, 1007 |
| POST | `/api/couple/join` | `code` | `coupleId`, `partner` | 1003, 1007, 1008 |
| GET | `/api/couple/info` | — | `coupleId`, `myAvatar`, `myNickname`, `partnerAvatar`, `partnerNickname`, `nicknameMine`, `nicknamePartner`, `togetherDays`, `mealDays`, `myLove`, `partnerLove`, `anniversary`, `theme`, `remindEnabled` | 1002 |
| POST | `/api/couple/settings` | `anniversary`, `theme`, `remindEnabled`, `nicknameMine` | — | 1002, 1013 |
| POST | `/api/couple/unbind` | — | — | 1002 |
| POST | `/api/user/delete` | — | — | 1001 |

> `login` 免鉴权；其余全部走 `AuthInterceptor`。所有接口**不接受** `coupleId` 入参（见 `../00-全局约定.md §4`）。
>
> **`couple/settings` 里为什么还留着 `nicknameMine`**：它是「专属称呼」（`couple.nickname_a/b`），属于关系数据，不是用户资料。用户自己的昵称与头像走 `/api/user/profile`，两条线不要混。
>
> **「在一起天数」口径**：`DATEDIFF(今天, COALESCE(anniversary, DATE(create_time))) + 1`——**设了纪念日就按纪念日算**（情侣常把纪念日设在绑定之前，按绑定日算会显示"在一起 3 天"这种明显错的数），未设置才回落到绑定日；解绑后复合复活原记录（D6），两者都不变，天数连续。它与「一起吃饭天数」（打卡去重天数）是两个指标，不要混用。

## 3. 实现

### 3.1 登录

```
POST /api/auth/login   { code, agreedPrivacy }
```

1. `agreedPrivacy != true` → 直接拒绝 `1001`（PRD §5.1 未同意不得登录）。
2. 调 `jscode2session` 换 `openid`。**`session_key` 不落库**——本项目不解密用户数据，用不到。
3. 按 `openid` 查 `user`，无则插入。
4. 签发 JWT：payload `{uid, exp}`，HS256，有效期 30 天。**不放 `coupleId`**——关系随时可绑可解，放进去会导致解绑后 token 仍带旧关系。
5. 返回 `{token, userId, nickname, avatar, hasCouple}`。

> 头像昵称走小程序头像昵称填写能力（`<button open-type="chooseAvatar">` + `<input type="nickname">`），
> `getUserProfile` 已废弃，不再使用。**登录时拿不到可靠头像**——`chooseAvatar` 返回的是临时路径，
> 具体上传与保存见 §3.6（D16）。

**静默重登（1001）**：前端 token 失效时由 `request.ts` 捕获 1001 自动调用本接口——带最新 `code` 与 `agreedPrivacy: true`（用户此前已授权，重登直接带 true，避免后端再判 1001 形成死循环），成功后刷新本地 token 并重放原请求；若重登本身仍失败，前端 `reLaunch` 到登录页（见 `前端-00-基础设施.md §4.1 / §8`）。

### 3.2 生成邀请码

`POST /api/couple/invite`

1. 已有 `status=1` 的关系 → `1007 已有情侣关系`。
2. 限频：近 1 小时生成 ≥5 次 → `1006`（用 `idx_couple_invite_creator_time` 统计）。
3. `SecureRandom` 生成 6 位数字，插入；`uk_couple_invite_code` 冲突则重试，最多 5 次。
4. `expire_time = now + 24h`。

### 3.3 加入（全程一个事务）

`POST /api/couple/join`

1. `select ... for update` 锁住该码（防两人同时用同一码）。
2. 校验 `status=0` 且 `expire_time > now`，否则 `1003`。
3. `creator_id == me` → `1008 不能和自己绑定`。
4. 双方都不存在 `status=1` 的关系，否则 `1007`。
5. `user_a = min(me, creator)`，`user_b = max(...)`。
6. 查 `uk_couple_pair`：**已存在历史记录则复活**（`status=1, unbound_time=null`），否则 insert（D6）。
7. 码置 `status=1, used_by=me, used_time=now`。

### 3.4 解绑

逻辑删除：`couple.status=0, unbound_time=now`。**记录保留**，双方本地历史仍可查看。
解绑后 `GET /api/couple/info` 返回 `1002`，前端 `reLaunch` 到配对页。

### 3.5 账号注销（真实删除）

PRD §13 第 3 条是合规 P0：**逻辑删除不满足「删除权」**，个人身份数据必须真删。

| 数据 | 处理 | 理由 |
|---|---|---|
| `user` 行（`openid` / `nickname` / `avatar`） | **物理 `DELETE`** | `openid` 就是身份标识，留着等于没删 |
| 头像文件 | 删磁盘文件 | 防止"库里没了、URL 还能访问" |
| 本人上传的打卡图片 | 删 `meal_checkin_image` 行 + 磁盘文件 | 照片属个人信息，可能含本人肖像与住处 |
| `couple` | `status=0, unbound_time=now` | 另一方还要看自己的历史，不能连带清空 |
| 约定 / 爱心值 / 打卡文本 / 通知 | 保留，用户侧展示为「已注销用户」 | 对方的历史与爱心值不该因一方注销归零；此时已无身份标识 |
| 本人未使用的邀请码 | `status=3` 作废 | 防注销后码还能绑上 |

**执行顺序**（一个事务，先库后文件）：

1. 存在 `status=1` 的关系 → 先按 §3.4 解绑。
2. 删 `meal_checkin` 中 `user_id=me` 的图片行，收集待删文件路径。
3. 作废本人未使用的邀请码。
4. `DELETE FROM user WHERE id = ?`。
5. **事务提交后**删文件；单张失败只记 `WARN`，不回滚（文件删除幂等，可补脚本，不能因 IO 失败让用户注销不掉）。

**注销后 token 立即失效**：`AuthInterceptor` 解析 token 后按 `uid` 主键查 `user`，查不到返回 `1001`。
这一次主键查询成本可接受，顺带堵住"token 只带 uid、用户已删仍能访问"的漏洞。

**二次确认在前端**：服务端不设 `confirm` 参数——交互拦截由前端做，服务端只保证鉴权正确。

### 3.6 头像上传与资料保存（D16）

**为什么必须自己上传**：`<button open-type="chooseAvatar">` 回调给的是 `e.detail.avatarUrl`，形如 `http://tmp/xxxx.jpeg`——这是**客户端临时文件路径**，只在当前会话有效，直接存库第二天就 404。`getUserProfile` 已废弃且不再返回可持久头像，没有"拿微信 CDN 地址"这条路。

**第一步：上传** `POST /api/user/avatar`（multipart 单张）

1. 类型白名单 `jpg/png/webp`，原始 ≤2MB，否则 `4001` / `4002`。
2. **重编码**：长边压到 256，JPEG 质量 0.8，循环降质直到 ≤100KB；重编码天然剥离 EXIF。
3. **同步审核**：拿重编码后的字节调 `security.imgSecCheck`（小图同步接口，限额 1MB / 750×1334，我们远小于）。
   - 未通过 → 直接 `4003`，**不落盘**。头像是 UGC，微信要求开发者自行检测，不做会被驳回。
   - 接口异常（非内容问题）→ `5001`，让用户重试；不要因为审核服务抖动就把用户挡在外面。
4. 落盘 `/data/upload/avatar/{userId}_{yyyyMMddHHmmss}.jpg`，**同时删旧头像文件**（旧路径从 `user.avatar` 读）。
   文件名带时间戳而不用固定 `{userId}.jpg`，是为了绕过微信/浏览器对同 URL 的强缓存。
5. 返回 `{ avatar }`（相对路径）。**此步不写库**，与打卡上传一致。

**第二步：保存** `POST /api/user/profile`

```
{ nickname?, avatar? }      // 两者至少传一个
```

- `nickname`：≤64 字，走 `msgSecCheck` 文本检测（昵称同属 UGC）。
- `avatar`：必须是**本服务上传过的路径**——校验前缀 `/upload/avatar/` + 文件存在 + 归属当前用户（文件名含 `userId`），任一不满足返回 `4004`，防越权引用他人头像。
- 返回更新后的 `{ nickname, avatar }`，前端就地更新 `appState.user`。

> **前端两步走**：`chooseAvatar` 拿到临时路径 → 先上传拿到相对路径 → 再随昵称一起保存。上传成功但保存失败时，前端要留住已上传的 `avatar` 路径，重试不必重传。

### 3.7 关系信息（`GET /api/couple/info`）

一次返回关系卡片所需的全部数据，**两个天数分开算**：

```sql
-- 在一起天数：优先用自定义纪念日，未设置才回落到绑定日（spec: 「以自定义日期作为在一起天数的计算基准」）
SELECT DATEDIFF(CURDATE(), COALESCE(anniversary, DATE(create_time))) + 1 AS togetherDays
FROM couple WHERE id = #{coupleId} AND status = 1;

-- 一起吃饭天数：有打卡的日期去重（与报告口径一致，按打卡记录算，不看图片审核状态）
SELECT COUNT(DISTINCT p.plan_date) AS mealDays
FROM meal_checkin c
JOIN meal_plan p ON p.id = c.plan_id
WHERE p.couple_id = #{coupleId};
```

`mealDays` 不加日期范围——这是**累计**值；期间值由 `GET /api/report?scope=month|year` 的 `checkinDays` 承担。

**出参按调用者视角**（`my*` / `partner*`），不暴露 `user_a` / `user_b` 的中性排序：服务端按 `UserContext` 里的当前用户判定谁是"我"，前端无需再比对 `userId`。

- `nicknameMine` = 我对对方的专属称呼，`nicknamePartner` = 对方对我的专属称呼（存储仍是 `nickname_a` / `nickname_b`，返回时按视角映射）。
- `anniversary` 为 `yyyy-MM-dd` 字符串，未设置返回 `null`；`remindEnabled` 读 `couple.remind_enabled`（默认 1）。

## 5. 验收要点

对照 `openspec/changes/bootstrap-mvp/specs/couple-binding/spec.md`：

- [ ] `agreedPrivacy != true` 调用登录返回 1001
- [ ] 6 位码 24h 有效、一次性；重复使用返回 1003
- [ ] 自己用自己生成的码返回 1008
- [ ] 双方任一已有有效关系返回 1007
- [ ] 解绑后记录保留（`status=0`），历史仍可查
- [ ] 解绑后再用同一对用户绑定 → **复活原记录**，不报 `uk_couple_pair` 冲突
- [ ] 1 小时内第 6 次生成邀请码返回 1006
- [ ] 注销后 `user` 行物理不存在，旧 token 访问任意接口返回 1001
- [ ] 注销后本人打卡照片（行 + 文件）已删除，对方历史仍在且显示「已注销用户」
- [ ] 上传头像后库里存的是相对路径，换设备/次日仍能正常显示（不是 `http://tmp/` 临时路径）
- [ ] 头像未过审返回 4003，且 `/data/upload/avatar/` 下**没有**该文件
- [ ] 传他人头像路径（文件名是别的 `userId`）返回 4004
- [ ] 换头像后旧头像文件已删除，同一 URL 不会因缓存显示旧图
- [ ] `couple/info` 同时返回 `togetherDays` 与 `mealDays`，两者数值不同（前者从建关系起算，后者按打卡去重）

## 6. 易错点

| 坑 | 说明 |
|---|---|
| token 里放 `coupleId` | 解绑后 token 仍带旧关系，会导致越权读到别人数据。**只放 `uid`** |
| 绑定时直接 insert | `uk_couple_pair` 对上已解绑的记录会冲突。**必须先查历史记录决定 update / insert**（D6） |
| 忘记规范化 `user_a < user_b` | 两人分别绑定时顺序不同会产生两条关系。`CHECK` 会在插入时报错，但更好的是应用层先排序 |
| 邀请码冲突直接抛异常 | `uk_couple_invite_code` 是 6 位数字空间，撞码正常，**应重试最多 5 次** |
| 注销时先删文件后提交事务 | 事务回滚了文件却删了，用户数据还在但照片没了。**必须先库后文件** |
| 直接把 `chooseAvatar` 的 `avatarUrl` 存库 | 那是 `http://tmp/` 临时路径，**当天之后全部 404**。必须上传换取相对路径（D16） |
| 头像用固定文件名 `{userId}.jpg` | 微信与浏览器会对同 URL 强缓存，换头像后界面还是旧图。**文件名带时间戳** |
| 头像校验只查前缀不查归属 | 用户把他人的 `/upload/avatar/{别人id}_x.jpg` 填进来就能盗用头像。**文件名必须含自己的 `userId`**（4004） |
| 昵称不走文本检测 | 昵称与头像同属 UGC，只审图不审字照样会被驳回 |
